Debugging 65C64 programs (DebuggerPlan.txt F3, plan, 2026-11-24)
=================================================================

The user (2026-11-24): "Plan out how to debug 65C64 programs".  Nothing here is a go-ahead to build: the decisions at
the end are the user's, and each stage is brought up before it is started.

Every decision made 2026-11-24 (see the end): waiting for the user to say when to build.

Today the IDE debugs W65C816 programs on the HCP65 in its emulator (DebuggerPlan.txt A to E): Call Stack, Locals,
Autos, Watch, QuickWatch and data tips.  The goal is the same windows, unchanged, for a program built by a 65C64
configuration, Debug or Release.

Reworked 2026-11-24 after the user's "Reconsider this plan in terms of release builds (you're focusing on V as the
only frame again, which it needn't be)": the first drafts described a 65C64 frame by V.  A Release build's frame may be
found from S, from V, or from any register holding a copy of S (the 65C64's psh and pul take any of A, B, S, V, W, X
and Y as their stack register), and V may hold a value instead.  So nothing here is built on one frame register: a
frame is described from a fixed address, and which register finds that address is described per function.


What there is to build on (surveyed 2026-11-24)
-----------------------------------------------

Running and stepping:
  - MicroprocessorLib's CFast65C64 runs 65C64 code; the asm, C++ and Libc65 tests run their programs on it, with
    memory and the host file device at 00FF:0200 (Assembler65Lib's Asm65HostFiles.h, Libc65's host.h: files and the
    console's output).  That is the only 65C64 machine there is: the emulator has no 65C64 computer.
  - EmulatorDebugLib has CFlat65C64DebugTarget (a CFast65C64 with flat memory) and CFast65C64DebugDecoder (the
    disassembly), but only TestDebugServer uses them: there is no emulator program for the IDE to start.
  - BuildLib builds 65C64 configurations (BT_65C64, CPPT_65C64; images and executables), and the IDE's debugger
    knows nothing of the processor but its register names (the emulator describes them).  A 65C64 configuration has
    no default emulator (CIDEDebugging::ChooseTool gives one to W65C816 configurations only).

The compiler (CommonLibraries/Libraries/CppCompilerLib):
  - The front end's debug records are the target's: .dfunction (with its result type), .dvariable, .dglobal, .dtype.
    Two things are the W65C816 back end's alone: where each kept slot ended up (CIRWrittenFunction::AddSlot,
    IRW65C816Backend.cpp) and the .dframe after the prologue (CIRBackend::DescribeFrame is empty for the 65C64).  So a
    65C64 build has functions and types but no frames and no variable places.
  - Variables are only described in Debug mode (CCPP65IRFrontEnd::DescribeVariables runs when Debuggable): a Release
    build of either processor has none, so its Locals are empty.  DebuggerPlan.txt's decision 1 said Release shows
    the variables still in memory; that was never built.
  - 65C64 frames (IR65Backend.h SIR65Frame, Prologue): jsr pushes a 4 byte return address (and P if asked); the
    stack is post-decrement (65C64Simulator.txt: pushing n bytes stores them at S-n+1 ... S).  A framed function:
    `psh V; sub S, n; cpy V, S`, its frame [1 + offset + V], the caller's V and the return address above it, then the
    arguments; the [$80 + W] pseudo registers it keeps (callee saved) pushed after the frame.  A frameless function
    doesn't set V up and finds its arguments from S; a bHomeV function uses V for a value, saving the caller's V
    first.  W is 0 by convention; V is kept by calls.  Results are in A (all 8 bytes of a 64 bit one).
  - W65C816 frames are described by EAsm65DebugLink (Asm65DebugRecords.h), each a rule from D: ADL_None (D is the
    caller's), ADL_Frame (the caller's D at D + n + 1, the return address after it), ADL_SavedS (an aligned frame:
    S after phd kept at [D + n]), ADL_User (a kernel's interrupt from user mode: the process's D and S pushed on the
    kernel's stack).  Variables are at D + offset (ADW_Frame) or where the pointer there points (ADW_Indirect).

The debugger (Assembler65Lib, CppCompilerLib, the IDE):
  - CAsm65StackWalker is the W65C816's (Asm65StackWalker.cpp, 713 lines).  What isn't: the records added for each
    space (AddRecords), finding a PC's function (Find), the walk loop (Walk), and Locate (but for its 16 bit frame
    place and 3 byte pointer).  What is: Caller and its three ways (Entering: following the instructions from the
    function's start, S's distance below its entry S and the copies of S in A, X and Y; Returning: following them to
    the rtl; Linked: by the link kind from D), ReturnTo (jsl, jsr, an interrupt's P), the indirect call rule, and the
    instruction decoding.  SAsm65StackFrame and SAsm65StackRegisters are 16 bit (uiS, uiD) and the registers are the
    W65C816's.  CAsmW65C816FrameCheck, the oracle that says a walk is right, compares a walk's PC, S and D.
  - Its users: CCPP65DebugValues and CCPP65DebugWatch (Locate only), CIDEDebugStop (embeds one),
    TestAsm65StackWalker(Interrupts), TestCPPW65C816Debug and TestHCP65Kernal's Walk.
  - CCPP65DebugValues masks addresses to 24 bits and reads the vtable's pointers as the W65C816 lays them out;
    Result reads A and X as 16 bit halves.  CCPP65DebugWatch's built in types have the W65C816's sizes.  The records
    don't say which processor they are for.
  - CIDEDebugger::GetStackRegisters gives a walk the W65C816's registers only.  The IDE's windows need nothing.


The frame model (decided 2026-11-24, both processors)
-----------------------------------------------------

  A call's frame address is S as its caller had it just before the call: the return address is the bytes just below
  it, and it is the caller's S once the call returns.  It doesn't move while the call runs, so everything a debugger
  wants of the call is a fixed distance from it, whatever the code does with its registers:
    - its variables in memory (ADW_Frame: at the frame address + offset; ADW_Indirect: where the pointer there points);
    - the registers it saved for its caller, each at its own place (the caller's V, the [$80 + W] units it keeps; on
      the W65C816 the caller's D, and an interrupt's P);
    - its return address.
  What changes as the call runs is only how the frame address is found from the registers, and the records say that
  per function once its body runs (after its prologue, until its epilogue):
    - from a register and an offset: "frame address = R + k", for any register R: V after `cpy V, S`, D after tcd, S
      itself in a function whose S doesn't move in its body, or any register a back end keeps a copy of S in;
    - from a place in memory: "frame address = [R + k] + j" (the W65C816's aligned frame, S kept in the frame);
    - from S as it is at each instruction: the walker follows the instructions from the function's start to find S's
      distance from the frame address (as Entering does now), for a frameless function or one using its frame
      register for a value.
  Before the body (the prologue) and after it (the epilogue) the walker always follows the instructions.  The caller's
  registers are then the saved ones read back, S is the frame address (and what the entry pushed besides the return
  address), and every other register is as the callee has it (a register the callee changes without saving isn't
  one a caller can rely on across a call).

  The W65C816's link kinds are this model's rules: ADL_Frame n is "frame address = D + n + 5 (after jsl's 3 bytes),
  the caller's D saved below it"; ADL_SavedS is the memory rule; ADL_None is "follow S"; ADL_User is a kernel
  interrupt's caller in the other space, its S and D saved (S as a saved register, not the frame address).  So one
  walker interprets both processors' records, and a processor only has to say what the rules can't: how to follow its
  instructions, and how its calls and returns are encoded.

  Variables are at the frame address + offset in both builds of both processors.  Release describes the variables
  whose slot is the variable's own for the whole function (decision 2); never a packed slot another value may share.


What is to be built
-------------------

Stages in order; each builds, is checked and committed on its own.

A. The records describe frames by the frame model (Assembler65Lib, CppCompilerLib)
  A1. Records version 4: each function's frame rule (register and offset, or memory place, or "follow S"), its saved
      registers (register and place from the frame address), and the processor the records are for (so values,
      watches and the walker need no option: pointers are 32 bits on the 65C64, 24 on the W65C816).  Variables'
      offsets are from the frame address.  The assembler's directives say the same: .dframe names a register
      (`.dframe V, n`; `.dframe [D + n], j`; `.dframe none`), .dsaved names a saved register and its place.  The
      W65C816 back end's DescribeFrame and the kernal's hand written records (Start.asm, KernalInterrupts.asm,
      UserCalls.asm, Libc65's heap call) are rewritten in it: their walks don't change.
  A2. The 65C64 back end's DescribeFrame, for every shape it makes, Debug and Release: a framed function's rule from V
      and the caller's V saved; a bHomeV function's "follow S" and the caller's V saved where it pushed it; a
      frameless one's "follow S"; each kept [$80 + W] unit saved where the prologue pushed it.  Where each kept slot
      is (AddSlot, as the W65C816's does).  A shape a later back end change adds (a copy of S in another register)
      is one more rule, not a walker change.
  A3. Release variables (decided), both processors.  Surveyed 2026-11-24: the front end names a variable's slot
      (dbgN) and records it only in Debug mode (KeptSlot, AddDebugVariable, DescribeVariables), the W65C816 back end
      reports only volatile slots (IRW65C816Backend.cpp), and each slot has a frame offset of its own
      (IRW65C816Places.cpp), so a slot that survives is its variable's alone.  To build:
        - the front end names the slots and records the variables in Release too, not volatile;
        - the back ends report named slots, volatile or not (the 65C64's with A2);
        - the optimiser audit, the bulk: each pass that changes a named slot drops its name, so its variable is
          "not kept" rather than shown wrong: promoting it (mem2reg), splitting an object's slot, removing or
          delaying its stores (dead stores, stores moved out of loops), the inliner (a callee's slots become the
          caller's).  Passes that only remove or move loads leave it.  The Debug mode work's list of the passes that
          touch slots is the start;
        - tests: Release versions of TestCPPW65C816Debug's (and C2's 65C64) stack and values tests: an address taken
          variable, an array and an object right at their stops, a promoted variable "not kept".
      About a third of the first plan's stage A, most of it the audit.  What Release then shows: what stays in
      memory (objects, arrays, anything whose address is taken); scalars in registers stay "not kept" (F1).
  A4. Saved registers (decided): every register a function saves is described, not only the ones a walk needs, so
      a later F1 can show a caller's variable kept in a register its callee saved.
  A5. Tests: TestAssembler65Lib (the directives, linked and read back; each rule); TestCppCompilerLib (each frame
      shape's records on both processors); TestCPPW65C816Debug and TestHCP65Kernal's Walk unchanged (the W65C816's
      walks the same frame for frame under the new records).

B. One walker interpreting the frame model (Assembler65Lib)
  B1. CAsm65StackWalker becomes the interpreter (decision 4): the records, Find, Walk, Locate (from the frame
      address), and Caller by the rules: find the frame address, read the saved registers and the return address,
      make the caller's registers.  A processor's part (CAsmW65C816StackWalker, CAsm65C64StackWalker) gives only:
      following its instructions (S's distance from the frame address and the copies of S, in the prologue, the
      epilogue and code with no rule), its calls' and returns' encoding (return address bytes and adjustment, what
      an interrupt pushes), its indirect call rule, and its registers' names and widths.
      SAsm65StackFrame keeps the call's frame address and its registers (32 bit S, an array of the processor's
      registers) in place of uiS and uiD; SAsm65StackRegisters is the processor's registers by its own names, with
      an Init for each fast core.
  B2. The W65C816's part is today's Entering, Returning, ReturnTo, IsIndirectCall and Instruction, moved; Linked is
      gone (the rules are the base's).  Checked first, alone: TestAsm65StackWalker, TestAsm65StackWalkerInterrupts,
      TestCPPW65C816Debug, TestHCP65Kernal's Walk and the IDE's debug-* checks, every walk the same frame for frame.
  B3. The 65C64's part: following its instructions (psh and pul with any stack register, sub and add on S, copies of
      S into any register), jsr's 4 byte return address (P if pushed), brk and interrupts as 65C64Simulator.txt says
      they push.  Following relies on S being the same at an instruction whichever way the code got there (pushes
      only round calls), which the frame check proves.
  B4. CAsm65FrameCheck, split when the 65C64's is written: the base the calls followed, WrongFrame (comparing the
      frame address and the registers the rules restore) and the writes reported; each processor's decoding of calls
      and returns.
  B5. Tests: TestAsm65StackWalkerBase (a made up processor's frames, its part a few lines in the test: the base
      is no processor's); TestAsm65StackWalker65C64 (hand written frames of each shape, every step checked); every
      TestCPP65C64 program walked at every step, Debug and Release, against the frame check.  Kept as a test that
      runs, not a one off, for both processors: a back end change that saves a register somewhere new, keeps S in
      another register, or leaves S uneven across a branch must fail a test, not a debugging session.

C. Values and watches on the 65C64 (CppCompilerLib)
  C1. CCPP65DebugValues takes the address width and the vtable layout from the records' processor; Result reads A
      (up to 8 bytes) on the 65C64.  CCPP65DebugWatch's built in types are the processor's sizes.
  C2. TestCPP65C64Debug: TestCPPW65C816Debug's tests (frames, stack, values, edits, watches, windows) made generic
      and run on both processors, Debug and Release (Release's: the frames, and the variables A3 keeps).

D. An emulator to debug 65C64 programs in (decision 5): HCP65/X65C64-Emulator (the user, 2026-11-24)
  D1. A 65C64 emulator, the HCP65 repository's X65C64-Emulator project (beside HCP65-Emulator, with its Visual Studio
      project and a Linux CMake build as HCP65-Emulator has): CFlat65C64DebugTarget with the host file device (stdio to
      its console), loading the image a 65C64 configuration builds at its address and running it from its entry; debuggable by EmulatorDebugLib's
      launch arguments (--debug-shm, --debug-tcp, --debug-wait), quitting when the program stops (stp) or the
      debugger goes.  A console program: no window, so the checks need no reference screen.
  D2. The IDE: a 65C64 configuration's default emulator is it; CIDEDebugger::GetStackRegisters gives the processor's
      registers by the names the target describes, and the walker for the processor the emulator says it is
      (NewAsm65StackWalker: a processor's name to its walker).  The windows are unchanged.

E. Checks
  E1. The IDE's debug-* checks run on Checks/Input/Debugging built for the 65C64 too (each check given the
      configuration, not written twice), and debug-optimised shows Release's kept variables on both processors.
  E2. The website's debugging.md: the 65C64, and what a Release build shows.

What is built
-------------

  - A1, B1, B2 (2026-11-24): records version 4 and the frame model; the walker split into CAsm65StackWalker and
    CAsmW65C816StackWalker (HCP65 2eb8ef4, CommonLibraries 0f53e5129, HCP65-IDE 1542d04).  The W65C816's walks are
    unchanged frame for frame.
  - A2 (CommonLibraries c95b0fd20): the 65C64 back end's DescribeFrame reads the prologue after the body's label: a
    framed function's `.dframe V, n` and `.dbase V`, a frameless or bHomeV one's `.dframe none`, the caller's V and each
    kept [$80 + W] unit as .dsaved.  A register function's body is an entry of its own (a .dfunction after its label),
    since its stub pushes and calls it.  CIRBackend::AddVariableSlots serves both back ends (VariableSlotPlace each).
    Kept pseudo-register units can't be produced from C++ yet: TestIR65Backend's DescribeFrame test covers them.
  - A3 (CommonLibraries 167ebe50c): Release variables, both processors.  The front end records each variable whenever
    the unit has a line table (DescribesVariables), Debug or Release, and names its slot dbg<n> after the function's
    fingerprint is taken (NameVariableSlots: a profile measured with a line table matches the build without one); the
    slot is only kept (volatile) in Debug.  The back ends report named slots (CIRBackend::VariableSlotName), and the W65C816's keeps their stores.
    The optimiser audit: no IR pass removes or moves a store (HoistCommon, HoistInvariants and SinkLoads only take
    what has no effect, or loads; RemoveDeadCode keeps stores; ReplaceLoopIdioms' memset does the same stores);
    promotion removes the slots it takes; the inliner gives a callee's slots no names; SplitSlots forgets the split
    slot's name (CIRFunction::ForgetTemporaryName).  The 65C64 back end removes no stores, and every slot has frame
    bytes of its own on both.  Parameters stay Debug only (copying them to a slot costs Release code).  Tests:
    TestCPP816DebugRelease (main's array, object and address taken int read right from a callee's stop, a folded
    int "isn't kept"), the 65C64's Release records in TestCPP65C64DebugFrames (a split array not kept; the same
    program's memory variables in the frame), TestIROptimiserSplitSlotNames.
  - A4: every register a function saves is described (A1's W65C816 records; A2's 65C64 V and kept units).

Things to watch for
-------------------

  - Other sessions work in the 65C64 back end (IR65Backend, its registers V, W and B): ListAgents and git log before
    A2-A3, and tell them before changing the prologue, SIR65Frame or what DescribeFrame reads.
  - The W65C816's walks must be the same frame for frame through A1 and B1-B2 (records rewritten, walker split):
    TestAsm65StackWalker, TestAsm65StackWalkerInterrupts, TestCPPW65C816Debug, the kernal's Walk, the IDE's checks.
  - The kernal's hand written records (Start.asm's stubs, KernalInterrupts.asm, UserCalls.asm, Libc65's heap call) are
    rewritten in A1's directives: their .dframe user, n becomes saved S and D.
  - Records version 4 makes every .debug file stale: the kernal's and programs' are rebuilt by their builds.
  - Release variables (A3) must never show a slot that holds another value at the stop (DebuggerPlan.txt's "Things
    to watch for"): only slots the back end says are the variable's own for the whole function.
