Debugging 65C64 programs (DebuggerPlan.txt F3, plan, 2026-11-24)
=================================================================

The user (2026-11-24): "Plan out how to debug 65C64 programs".  Nothing here is a go-ahead to build: the decisions at
the end are the user's, and each stage is brought up before it is started.

Today the IDE debugs W65C816 programs on the HCP65 in its emulator (DebuggerPlan.txt A to E): Call Stack, Locals,
Autos, Watch, QuickWatch and data tips.  The goal is the same windows, unchanged, for a program built by a 65C64
configuration.


What there is to build on (surveyed 2026-11-24)
-----------------------------------------------

Running and stepping:
  - MicroprocessorLib's CFast65C64 runs 65C64 code; the asm, C++ and Libc65 tests run their programs on it, with
    memory and the host file device at 00FF:0200 (Assembler65Lib's Asm65HostFiles.h, Libc65's host.h: files and the
    console's output).  That is the only 65C64 machine there is: the emulator has no 65C64 computer.
  - EmulatorDebugLib has CFlat65C64DebugTarget (a CFast65C64 with flat memory) and CFast65C64DebugDecoder (the
    disassembly), but only TestDebugServer uses them: there is no emulator program for the IDE to start.
  - BuildLib builds 65C64 configurations (BT_65C64, CPPT_65C64; images and executables), and the IDE's debugger
    knows nothing of the processor but its register names (the emulator describes them).  A 65C64 configuration has
    no default emulator (CIDEDebugging::ChooseTool gives one to W65C816 configurations only).

The compiler (CommonLibraries/Libraries/CppCompilerLib):
  - The front end's debug records are the target's: .dfunction (now with its result type), .dvariable, .dglobal,
    .dtype, Debug mode's kept slots (mbDebuggable).  All of it is written for the 65C64 too, but two things are the
    W65C816 back end's alone: where each kept slot ended up (CIRWrittenFunction::AddSlot, IRW65C816Backend.cpp) and
    the .dframe after the prologue (CIRBackend::DescribeFrame is empty for the 65C64).  So a 65C64 Debug build has
    functions and types but no frames and no variable places.
  - 65C64 frames (IR65Backend.h SIR65Frame, Prologue): jsr pushes a 4 byte return address; `psh V; sub S, n;
    cpy V, S`; the frame is [1 + offset + V], then the link (8 bytes: the caller's V and the return address), then the
    arguments; the [$80 + W] pseudo registers a function keeps are pushed after the frame.  A frameless function
    doesn't set V up and finds its arguments from S, and one with bHomeV uses V for a value (saving the caller's
    first).  Results are in A (all 8 bytes of a 64 bit one).  The stack is post-decrement (65C64Simulator.txt).

The debugger (Assembler65Lib, CppCompilerLib, the IDE):
  - CAsm65StackWalker is the W65C816's: its prologue and epilogue sweeps decode W65C816 instructions, its link is D,
    and its entries are jsl, jsr and interrupts.  CAsmW65C816FrameCheck, the oracle that says a walk is right, is
    the W65C816's too.
  - CCPP65DebugValues masks addresses to 24 bits and reads the vtable's pointers as the W65C816 lays them out;
    Result reads A and X as 16 bit halves.  CCPP65DebugWatch's built in types have the W65C816's sizes (int is 16
    bits).  The records don't say which processor they are for.
  - CIDEDebugger::GetStackRegisters gives a walk the W65C816's registers only; a 65C64 has one space (it is always
    in kernel mode), so the stack spaces fall back to DEBUG_SPACE_ANY as they are.
  - The IDE's windows (CIDEDebugStop, CIDEValuesPane, CIDEDebugWindows) work on records, values and frames, and
    need nothing of their own.


What is to be built
-------------------

Stages in order; each builds, is checked and committed on its own.

A. The compiler describes 65C64 frames and variables (CppCompilerLib's 65C64 back end)
  The debugger finds each frame from whatever register has it (the user, 2026-11-24): the compiler describes the
  frames it makes, and doesn't make different ones for the debugger.  Debug and Release frames are made the same way
  (frameless functions and bHomeV stay in both); Debug mode only keeps the slots (the front end's, and no inliner).
  A frameless or bHomeV function never has frame bytes, so no kept variable is lost to it.
  A1. Where each kept slot is (AddSlot, as IRW65C816Backend does), so .dvariable gives a frame offset from V.
  A2. CIR65Backend::DescribeFrame says, for each function, which register its frame is in and where its caller's V
      is: .dframe frame, n after a framed prologue (the caller's V and the return address at V + n + 1); for a
      bHomeV function, the caller's V pushed at entry (a link kind for "saved at entry S + k", Asm65DebugRecords'
      EAsm65DebugLink, if none of the W65C816's fits); for a frameless one that leaves V alone, none (the caller's V
      is the V running).  The pushed pseudo registers come after the frame and don't move the link.  Where S is
      within the function is the walker's to follow (B2), not described.
  A3. The records say whose they are (records version 4: the processor, from the object's assembler), so values,
      watches and the walker need no option: pointers are 32 bits on the 65C64, 24 on the W65C816.
  A4. Tests: TestAssembler65Lib (a 65C64 object's records linked and read back), TestCppCompilerLib (each frame
      shape's .dframe: framed, bHomeV, frameless).

B. Walking a 65C64 stack (Assembler65Lib)
  B1. The walker split by processor (decision 2; planned in detail below, "The stack walker split").
  B2. CAsm65C64StackWalker, the same way in Debug and Release: a framed function's caller by its link from V; one
      whose frame isn't made yet (or that makes none, or keeps V as a value) by following its instructions from its
      start to its PC, S's distance below its entry S and the copies of S in registers, as the W65C816's Entering
      does; one taking its frame apart by its instructions to its rts, as Returning does.  That relies on S being
      the same at an instruction whichever way the code got there (pushes only round calls), which the frame check
      (B3) proves.  jsr's 4 byte return address; brk and interrupts as 65C64Simulator.txt says they push.
  B3. CAsm65C64FrameCheck: the oracle, as CAsmW65C816FrameCheck is, following jsr and rts (and interrupts).
  B4. Tests: TestAsm65StackWalker65C64 (hand written frames of each shape, every step checked); and every
      TestCPP65C64 program walked at every step in Debug and Release against the frame check, as the W65C816's were
      once (none may be wrong).  Kept as a test that runs (TEST_CPP65_WALK_ALL or a part of the suite), not a one
      off: other sessions change the 65C64 back end's registers, and a change that saves V somewhere new or leaves S
      uneven across a branch must fail a test, not a debugging session.

The stack walker split (B1, planned 2026-11-24)
  What it is now (HCP65/Libraries/Assembler65Lib/Asm65StackWalker.cpp, 713 lines): CAsm65StackWalker holds the
  records added for each space (AddRecords), finds a PC's function (Find), runs the walk (Walk: the innermost frame,
  then each caller until one isn't found or isn't above its callee on the same stack), and finds a variable (Locate).
  Those know nothing of the W65C816 but two things: Locate's frame place is 16 bits (bank 0) and an indirect
  variable's pointer is 3 bytes.  The rest is the W65C816's: Caller and its three ways (Entering, the sweep from the
  start; Returning, the sweep to the rtl; Linked, by .dframe from D), ReturnTo (jsl, jsr or an interrupt, P pushed),
  the indirect call rule, and its instruction decoding (opcode defines, widths).  SAsm65StackFrame and
  SAsm65StackRegisters are 16 bit (uiS, uiD) and the registers are the W65C816's (C, X, Y, P; Init from a
  CFastW65C816).  CAsmW65C816FrameCheck, the oracle, is the W65C816's and compares a walk's PC, S and D.
  Its users: CCPP65DebugValues and CCPP65DebugWatch (through the base: Locate only), CIDEDebugStop (embeds one),
  TestAsm65StackWalker(Interrupts), TestCPPW65C816Debug and TestHCP65Kernal's Walk (each embeds one and its
  registers).

  S1. The frame and registers become any processor's, and nothing else changes: SAsm65StackFrame's uiS is 32 bits and
      uiD becomes uiFrame, the frame register's value (D on the W65C816, V on the 65C64); SAsm65StackRegisters keeps
      uiPC, uiS, uiFrame and uiSpace, and the registers the processor's sweep follows go in an array by the
      processor's own names (EAsmW65C816StackRegister: C, X, Y, P; the 65C64's later: A, B, X, Y, W, P), with an
      Init for each processor's fast core.  EAsm65DebugLink's words say "frame register" for D.  The users change
      their uiD to uiFrame; CAsmW65C816FrameCheck::WrongFrame compares uiFrame.
  S2. The split: CAsm65StackWalker keeps Init, Kill, AddRecords, Walk, Find and Locate, and asks the processor's walker
      for its caller (Caller, pure virtual) and for the two things Locate needs (the frame place's address, wrapped
      as its processor wraps it, and a pointer's bytes: virtual FramePlace and PointerBytes).  The W65C816's code
      moves unchanged to CAsmW65C816StackWalker (AsmW65C816StackWalker.h/.cpp, beside CAsmW65C816FrameCheck, as the
      Assembler65Lib's W65C816 classes are named): Caller, Entering, Returning, Linked, ReturnTo, IsIndirectCall,
      ReadWord, Instruction and the opcode defines.  A move, not a rewrite: the diff of the moved functions is empty
      but for their class name.
  S3. Who makes which: each user names the class it needs (the tests and the kernal's Walk test are the
      W65C816's); CIDEDebugStop holds a pointer made for the processor the emulator says it is (the name
      CIDEDebugger::GetStackRegisters already checks), by one function in Assembler65Lib that maps a processor's name
      to its walker (NewAsm65StackWalker: "W65C816" now, "65C64" in B2), NULL for one without.  CCPP65DebugValues
      and CCPP65DebugWatch keep taking the base.
  S4. A test that the base is no processor's: TestAsm65StackWalkerBase walks a made up processor's stack (frames
      linked by a frame register, its Caller a few lines in the test), with Locate's place and pointer from it.
  S5. Checked: TestAssembler65Lib (TestAsm65StackWalker, TestAsm65StackWalkerInterrupts, the new base test),
      TestCPPW65C816Debug, TestHCP65Kernal's Walk, the IDE's debug-* checks; the IDE and the emulator build.  The
      W65C816's walks are the same frame for frame.
  The frame check is split when the 65C64's is written (B3), not before: a base for the calls followed, WrongFrame and
  the writes reported, and each processor's decoding of calls and returns.  Splitting it now would make a base with
  one user.
  Can be built before the machine is chosen (decision 1): it touches no emulator, and changes no walk.


C. Values and watches on the 65C64 (CppCompilerLib)
  C1. CCPP65DebugValues takes the address width and the vtable layout from the records' processor; Result reads A
      (up to 8 bytes) on the 65C64.  CCPP65DebugWatch's built in types are the processor's sizes.
  C2. TestCPP65C64Debug: TestCPPW65C816Debug's tests (frames, stack, values, edits, watches, windows) run on
      CFast65C64 from the 65C64 build, sharing the test code where the programs are the same (decision 4 of the
      first plan put the 65C64 after: its tests are the W65C816's made generic, not copied).

D. An emulator to debug 65C64 programs in (decision 1)
  D1. A 65C64 emulator: CFlat65C64DebugTarget with the host file device (stdio to its console), loading the image a
      65C64 configuration builds at its address and running it from its entry; debuggable by EmulatorDebugLib's
      launch arguments (--debug-shm, --debug-tcp, --debug-wait), quitting when the program stops (stp) or the
      debugger goes.  A console program: no window, so the checks need no reference screen.
  D2. The IDE: a 65C64 configuration's default emulator is it (as the HCP65 emulator is the W65C816's);
      CIDEDebugger::GetStackRegisters gives the 65C64's registers (by the names the target describes) and a
      CAsm65C64StackWalker is made for a 65C64 stop.  The windows are unchanged.

E. Checks
  E1. IDE checks on Checks/Input/Debugging65C64 (the W65C816 fixture's program, built for the 65C64): the same
      debug-call-stack, -frames, -watch, -autos, -data-tip, -quick-watch and -optimised checks, each W65C816 check
      given the fixture to run, not written twice.
  E2. The website's debugging.md says the 65C64 is debugged in its emulator.


What is the user's to decide
----------------------------

Asked one at a time, with my recommendation first.
DECIDED 2026-11-24: the debugger finds each frame from whatever register has it; Debug builds don't change frames
for it (A, B2).  It replaced the first draft's question 2 (Debug builds keeping the V chain).

  1. The machine to debug on.  There is no 65C64 computer in the emulator.  I recommend a flat 65C64 machine as the
     tests have (memory and the host file device, so printf works), as a small console emulator the IDE starts.
     The other way is to wait for a 65C64 computer to be modelled, with its own boards, which nothing plans yet.
  2. One walker split by processor (a shared base, each processor's caller finding its own) rather than a second
     walker beside the first.  I recommend the split (planned in "The stack walker split"): records, Locate and the
     walk loop are the same for both.
  2a. The split as a base class with a walker per processor (S2), or one walker holding a processor part it calls
     (composition).  I recommend the base class: only Caller and two small facts of Locate differ, and a
     processor part would be the same virtual functions behind one more object.
  2b. When to build the split: now, on its own (it changes no walk, S4 proves the base needs no processor), or as
     the first step of B once the machine is chosen.  I recommend with B: on its own it only moves code, and the
     65C64 walker is what shows whether the base is right.
  3. Where the emulator lives: the HCP65 repository beside HCP65-Emulator (it needs Assembler65Lib's host file
     device, which is there), or CommonLibraries beside EmulatorDebugLib.  I recommend HCP65.

My own choices, not asked: the records say their processor (A4); the 65C64's tests are the W65C816's made generic
(C2, E1); no measuring stage first, since the 65C64 has no ROM or memory limit Debug mode must fit (DebuggerPlan.txt
M's reason).


Things to watch for
-------------------

  - Other sessions work in the 65C64 back end (IR65Backend, its registers V, W and B): ListAgents and git log before
    A1-A2, and tell them before changing the prologue or SIR65Frame.
  - The W65C816 walker's tests (TestAsm65StackWalker, TestAsm65StackWalkerInterrupts, TestCPPW65C816Debug, the
    kernal's Walk) must pass unchanged through B1's split: the split moves code, it doesn't change it.
  - Records version 4 makes every .debug file stale: the kernal's and programs' are rebuilt by their builds.
