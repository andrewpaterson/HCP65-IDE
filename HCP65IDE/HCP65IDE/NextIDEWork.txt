5. Code completion, basic and smart: built 2026-11-26
-----------------------------------------------------

The user's decisions: it opens by itself only straight after "." "->" and "::", otherwise on Control+Space (basic)
or Control+Shift+Space (smart), not as an identifier is typed; smart is built with basic (2026-11-17).  The light
path and the kept parse both, from the start, with six points that make it friendly (2026-11-26, below).

CommonLibraries 70b41db52 (a driven chooser popup), 56a78ce5f (matches as good in the order added), 98d4890ec (a
row matched by its name only), bbe747140 (its page); HCP65-IDE: the commits after a8b0c3b named "Code completion".
Checks completion-member, -scope, -access, -name, -keys, -include, -parse, -by-type and -documentation, on
Checks/Input/Completion (CVehicle and CTruck with members of every access, a namespace, an enum, a typedef, a
template that holds, a header in a folder).

What was built (Docs/ide/editor.md's "Code completion" says it for the user):
  - The list (CIDECompletion): WindowLib's chooser popup, driven by the editor, which keeps the keys.  Complete Code
    (Control+Space) and by itself after "." "->" "::".  Members after "x." and "x->", base classes' too, by access
    from where the caret is (CIDEClassAccess reads a class's access from its text: the index hasn't it); what
    "N::" declares; what is in scope on a name by itself, the function's own first, then the language's words;
    #include's folders and headers.  Filtered as the name is typed, capitals matching.  Enter writes the entry, Tab
    in place of the whole name; a function with its brackets and Parameter Info (CIDEQuickInfo::ShowParameterInfoOf:
    the index hasn't seen the call yet); with one entry Complete Code writes it at once.
  - The light path (CIDELightTyper, IDECompletionContext): what is before the "." from the text and the index,
    with no parse: names, members, calls by what they return, indexings, "this", a cast in brackets, typedefs,
    "NS::CGauge".  It answers only what it is sure of.
  - The kept parse (CIDEExpressionTyper): the file checked on the edits thread (CIDECodeModel::RunEditsJob, one
    thing at a time with the edited files) with the expression in brackets where it was written, which is
    IntelliJ's dummy name done the other way round: nothing unfinished is left for the parser.  If "->" follows a
    class it is checked again as a call of its operator->.
  - Complete Code by Type (Control+Shift+Space, CIDEExpectedTypes): an argument's parameter, the left of "=", "=="
    and "!=", what the function returns, what a switch switches on; what is exactly the type first, then pointers
    to derived classes.
  - Control+Q with the list open: Quick Documentation of the selected entry, beside the list, following the
    selection (item 11's leftover).

The six points, as built:
  1. The list only grows: CChooserPopup::ItemsChanged keeps the selected item selected.  Built as said.
  2. The popup opens at once: where the light path has nothing it opens empty with "Working out what this is..."
     under its rows (a note, not a greyed row), and closes if the parse has nothing either.
  3. The parse is given a finished line: the expression in brackets, with a ";" if the line ends there.
  4. The kept parse a few keys old: this is the index, which the edits thread keeps up to date and the light
     path reads; and the file's last outline, for what function and class the caret is in.  No syntax tree is
     kept between keys.
  5. The light path offers only what it is sure of, with one exception the user DECIDED 2026-11-26 ("members appear
     at once"): "->" on a class template that isn't a pointer (Ptr<CGauge>) is taken to reach its first argument, at
     once, rather than waiting for the parse.  Ptr<M> is the only template in CommonLibraries, the IDE and LogiCim
     that defines operator->, and it returns M*, so the rule is right for all of today's code; a template whose
     operator-> returns something else would list the wrong class until the parse added the right one.  The parse
     is still asked.
  6. Smart completion doesn't wait: it uses the light path only, and the checked parse isn't asked for it.  So
     there is no "working" row to show; where the light path can't say what is wanted, the status line says so.

Where it differs from the plan:
  - The parse is asked after every "." and "->", whether the light path answered or not, as decided.  It costs a
    check of the file on the edits thread each time, behind which the file's highlighting waits.
  - Completion doesn't open by itself in an #include (the user's rule); Control+Space there.
  - Access: friends aren't known, so a friend's private members aren't offered to it.
  - A local variable is offered from the start of its function (the index has no block scopes); using directives
    aren't followed; macros aren't listed (the index has none).
  - Smart looks at the nearest 250 symbols in scope only (IDE_COMPLETION_SMART): each one's declaration is read
    for its type.
  - A list of what is in scope is of the names with a word starting with the first character typed, and is made
    again when that changes; before anything is typed, the nearest 500.

Measured (step 1), Release x64, the ModPlay workspace, in ModPlay.cpp, from the key to the list's entries (the
popup's own rows not timed): the members of a CModPlayer* 15 ms (19 entries); what is in scope starting "ui" 16 ms
(2,032 entries) and "C" 33 ms (21,709 entries); everything outside any scope, the first 500, 12 ms.  Before the
index was asked only for the names wanted (it copied every global symbol first) the member list took 385 ms.
The parse's time is the file's check's: not measured again (47 ms to 1.7 s, item 11's numbers).

Checked: TestWindowLib Debug x64 (24074 pass), from a private copy; the IDE's 566 checks on a private Release build,
all passing but enum-to-class, which failed before this work; the pages build with no warning of their own (the
site's build stops at another session's unfinished pages).  Not checked: an MSVC build; Windows; a real keyboard and

What was built: Reformat Code (Control+Alt+L, Edit menu) on the active file, or on the lines its selection is on;
and in Solution Explorer's menu on the selected file, or every C and C++ file of the selected folder, project or
solution.  One undo; the files are left changed, as a refactoring leaves them.  The status line says what changed.

The rules, each measured from CommonLibraries' 3819 sources first and shown to the user before the code:

  - a block's brace that ends a line goes on its own line;

    (Float4x4.cpp).  For the same reason white space is only added, never taken out, and nothing inside brackets
    is closed up.
  - A run keeps the column most of its names are in (half the headers' runs are further right than they need
    be); only a run with none lined up gets the first tab stop after its longest type.
  - Left as written, being the house's own: a body on one line; a class's friends and macros at the margin; its
    members indented further so their types line up after "virtual"; a pure function's "=0"; a declaration on
    its own written with one space.
  - No Optimise #includes tick: Optimise #includes works on the active file only.  No Settings page: nothing
    varied but the banner, which is a template already.
  - A prototype in Python settled the rules against the libraries; the C++ gives the prototype's text on all
    8231 files of CommonLibraries, HCP65-IDE and HCP65's libraries and kernal.  The prototype isn't kept.
