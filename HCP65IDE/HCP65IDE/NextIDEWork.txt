1. Find and Replace in the file
-------------------------------

What is missing: there is no Find or Replace within a file.  The only search is Find in Files (Ctrl+Shift+F,
CIDEFindInFiles) with its Current File scope.

What to build, as IntelliJ's: Ctrl+F opens a search bar over the editor (not a dialog), filled from the selection or
the word at the caret.  As the text is typed every match in the file is highlighted (CTextArea already highlights
occurrences: FindOccurrences, and the gutter's marks), the nearest is selected, and the bar says "3 of 17".  Enter or
F3 goes to the next, Shift+Enter or Shift+F3 to the previous, wrapping round.  Ticks for Match Case, Words and Regex
(item 2's engine), remembered in Settings.  Escape closes it and leaves the caret on the match.  Ctrl+R opens it with
a Replace field: Replace and Replace All, each one undo (CTextArea::ReplaceRanges), with Regex's $1 groups.  "In
selection" when the selection is more than a line.

Where: a bar component above CIDEEditorTab's editor; the search itself on CTextDocument so other text areas can use
it (WindowLib: tell 3c).  Ctrl+F and Ctrl+R are free in the keymap; F3 and Shift+F3 too.


2. Regular expressions, and Find in Files' file masks and Replace in Files
-------------------------------------------------------------------------

What is missing: Find in Files has Match Case and Whole Words only ("There are no regular expressions, file masks or
Replace in Files yet", navigation.md).  Nothing in the code has a regular expression engine: BaseLib has none, and
std::regex isn't used.

What to build:
  - A regular expression engine in BaseLib (CRegex), on CTextParser where it parses (the memory's rule): the syntax
    IntelliJ's find takes (Java's, which is ECMAScript's for what is used: classes, groups, alternation, the
    quantifiers lazy and greedy, anchors, \b, \d \w \s, escapes; $1 in replacements).  Compiled once to a backtracking
    matcher; tested in TestBaseLib.  Find (1) uses it too.
  - Find in Files: a Regex tick, and a File mask field ("*.cpp, *.h", with ! to leave out), both remembered.
  - Replace in Files (Ctrl+Shift+R): the Find tab's results with a Replace field; Replace All, or the ticked ones,
    as one undo across every file changed (the refactorings' undo already does this), open and closed files both.

Question for the user: is it right to write a regular expression engine, rather than use std::regex?  Code that runs
on the W65C816 (BaseLib is compiled for it) can't use the standard library yet, and the IDE's own code doesn't use it.


3. Go to Line
-------------

What is missing: no Go to Line.

What to build: Ctrl+G opens a small box over the editor, "Line[:column]" with the caret's place in it to begin with,

4. Code completion
------------------

What is missing: no completion while typing.

What to build, as IntelliJ's basic completion: Ctrl+Space, and by itself after "." "->" and "::", and as an
identifier is typed after a short pause.  A popup list of what can be written there, filtered as more is typed (camel
humps: "GSN" finds GetSelectedNode), each with its icon, its type or signature, and its class or namespace; Enter or
Tab writes it (Tab replaces the rest of the word), a function with its "(" and the caret between ")" when it takes
arguments; parameter info (Ctrl+P) after it.  What can be written comes from the code model (CCPPIndex, CIDECodeModel):
  - after "x." or "x->", the members of x's type, inherited ones too, by access from where the caret is;
  - after "N::", what N declares;
  - otherwise what is in scope: locals and parameters (the function's own syntax tree), the class's members, then
    the namespaces' and the globals';
  - #include "..." completes paths from the include directories; keywords too.

The type of an expression is the hard part: the index knows declarations, not expressions.  The compiler's binder
(CCPPBinder) works types out; Introduce Variable already asks the compiler for an expression's type (compile check):
see how and whether it is quick enough for a keypress, or whether a lighter path through the index is needed for
"name.member" chains.  Measure on the ModPlay workspace: under about 100ms from the key to the popup.

Questions for the user: does completion pop up by itself as an identifier is typed (IntelliJ does), or only after "."
"->" "::" and on Ctrl+Space?  Is a second, "smart" completion (Ctrl+Shift+Space: only what has the type expected
there) wanted now or later?


5. Automatic indenting, and the editor's other line commands
-----------------------------------------------------------

What is missing: Enter starts the new line at the margin ("no automatic indenting"); Tab types spaces while the
refactorings and the house style use tabs.

What to build: Enter keeps the line's indent, one more after "{" (and the "}" typed on a line of its own goes back
one), using tabs or spaces as the file does.  Then IntelliJ's line commands that aren't there: Ctrl+/ comments or
uncomments the line or the selected lines (//), Ctrl+Shift+/ the selection (/* */); Tab and Shift+Tab indent and
unindent the selected lines; Ctrl+Shift+Up/Down move the line or the selection.  Check which exist in the keymap
(Ctrl+D Duplicate does) before writing them.

Question for the user: should Tab type a tab (the house style), or keep typing spaces?  And is Reformat Code
(Ctrl+Alt+L, the house style's layout: tabs, names lined up in columns) wanted?  That is a large item of its own.


6. Bookmarks
------------

What is missing: no bookmarks.

What to build, as IntelliJ's: a toggle on the line (a mark in the gutter, beside breakpoints and listings), mnemonic
bookmarks 0-9 and A-Z, next and previous, and a Bookmarks tool window listing them by file; saved with the workspace
(.hcp65user, as breakpoints are) and moved by edits as the usages' places are (CIDEDocumentAnchor).

Question for the user: IntelliJ's toggle is F11, which is Step Into here (the Visual Studio key).  Which key?  In
the keymap now, F2, Ctrl+F11 and Ctrl+Shift+F11 are free: offer Ctrl+F11 for the toggle, Ctrl+Shift+F11 for a
mnemonic one and F2 / Shift+F2 for the next and previous (Visual Studio's Ctrl+K pairs need chords).


7. Context menus
----------------

What exists: the editor (Go to Source, Find Usages, Show Context Actions, Rename, Refactor, Cut, Copy, Paste) and
Solution Explorer have right-click menus (WindowLib's CComponent::SetContextMenu, the Menu key and Shift+F10 too).

What to build: menus on the rest, each with what that place does and what its keys do:
  - the Build tab: Copy, Copy All, Go to the message's line, Clear;
  - the Find Usages and Duplicates trees: Go to, Exclude, Remove, Expand All, Collapse All, Copy;
  - the Find (Find in Files) tab and the Run and Debug tabs: Copy, Clear, and what each tab's own toolbar does;
  - the Claude tab: Copy, Clear, Stop;
  - a diff tab: Next and Previous Difference (F7, Shift+F7), Copy;
  - the document tabs (they have one from WindowLib's dock: check it has Close, Close Others, Close All, Copy Path,
    Show in Solution Explorer);
  - the editor's: Go to Definition, Find Usages, Ask Claude about the selection, Add to Breakpoints, Compare with...
Rules (memory): a PopupClosed override calls its base; the menu goes on the page or container.  Check on Linux (X11)
too.


8. A tree that makes components only for the rows in view (WindowLib)
--------------------------------------------------------------------

What is wrong: CTreeContainer::AddNodeRow makes a grid, indent, chevron, icon and label for every row that can be
seen, and UpdateRows makes them all again when a node opens or closes.  Find Usages of 20,004 places in one file
took 1.7s to build and 2.5s more to lay out and paint, so Find Usages' files start closed past 1000 usages
(IDE_USAGES_OPEN_FILES_MAXIMUM, IDEUsages.cpp).

The direction the user agreed on 2026-11-10 ("Only visible components (active) sounds like the right solution"; and
"don't do anything yet": so ask before starting):
  - rows are worked out, not laid out: one row height, row i at i x height (maiRowNodes already lists the rows);
  - CListContainer's selection, keys, hover and highlights ask through three virtuals (how many rows, where row i is,
    which row is at y) instead of reading its grid; menus, combo boxes and dialog lists keep the grid;
  - the tree keeps a pool of about 50 row components for what its scroll view shows, bound again as it scrolls;
  - a row's width from CFont::CalculateWidth, kept per node, not from its label;
  - TestTree.cpp and TestList.cpp may look at row components: add a 100,000-node test that the components stay few.
The tree's public interface shouldn't change.  Then the 1000-usage rule goes.  WindowLib: 3c is in it now.
