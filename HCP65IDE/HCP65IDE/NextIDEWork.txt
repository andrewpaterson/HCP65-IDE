5. Code completion, basic and smart: OPEN
-----------------------------------------

Nothing of it is built: no completion command, no popup, Control+Space and Control+Shift+Space free.

What the user decided (2026-11-17): it opens by itself only straight after "." "->" and "::"; otherwise on
Control+Space (basic) or Control+Shift+Space (smart), not as an identifier is typed; smart is built with basic.

What to build is as it was planned:
  - Basic: a popup list of what can be written there, filtered as more is typed (camel humps: "GSN" finds
    GetSelectedNode), each with its icon, its type or signature, and its class or namespace; Enter or Tab writes it
    (Tab replaces the rest of the word), a function with its "(" and the caret between the brackets when it takes
    arguments, and parameter info after it.  After "x." or "x->", the members of x's type, inherited ones too, by
    access from where the caret is; after "N::", what N declares; otherwise what is in scope (locals and
    parameters, the class's members, then the namespaces' and the globals'); #include "..." completes paths from
    the include directories; keywords too.
  - Smart: only what has the type expected where the caret is, ranked by how close the type is: an argument (the
    parameter's type, from the call's overloads), the right of "=", a return, an initialiser, a case label (the
    switch's enum's enumerators); with what converts (a derived class's pointer for a base's).

What has changed since it was planned, and what that does to the plan:
  - Built since, to use and not write again: the chooser popup with its rows found as typed (CChooserPopup),
    CNameMatcher (camel humps, Go to's), Parameter Info (View.ParameterInfo, Control+P, CIDEQuickInfo), the file's
    outline from the edits thread (CIDEOutline), the symbol's info and icon (Quick Definition, Type Info), the
    caret's context (SIDECaretContext), class bases (FindClassBases).
  - The question this file left open is answered by a measurement.  The type of the expression at the caret from a
    checked parse of the file (Type Info's follow-up 3f, HCP65-IDE 21b5a91) took 47 ms in a BaseLib file and 1.7 s
    in IDEUsages.cpp, each press.  That is too slow for a key: completion can't parse the file when asked.
  - Two ways to the type of what is before the "." were weighed:
      a. a light path: the name's declaration from the function's own syntax tree (the edits thread already has
         it) and the index, then member by member along a "name.member->member" chain, with no binder.  Covers
         names, members, calls by their result, casts; not operators that are overloaded, nor templates'
         arguments unless the index has them (not looked at);
      b. the checked parse on the edits thread, kept up to date after each edit, so a key only reads what is
         there.

DECIDED by the user, 2026-11-26: both from the start, a answering at once and b adding to the list when it arrives,
made friendly to use by these, which are part of the item:
  1. The list only grows.  What the parse brings is merged in; the selected row stays selected and where it is on
     the screen.  A list the user hasn't touched yet may be sorted again.
  2. The popup opens at once.  If the light path can't type the expression it opens with one greyed row saying it
     is working, filled in when the parse lands; typing goes on, Escape closes it.
  3. The parse is given a finished line: a copy of the text with a dummy name at the caret ("x." as
     "x.__caret__"), as IntelliJ does.  Not tried on this parser yet.
  4. The kept parse is used when it is a few keys old: the declarations above the statement being typed are read
     from the last good parse, their places moved by the edits (as CIDEDocumentAnchor moves places); the statement
     itself is the light path's.
  5. The light path offers only what it is sure of: at an overload it can't pick or a template it can't see
     through it stops and leaves the answer to the parse.
  6. Smart completion shows the same "working" row while it waits for the expected type.
A follow-up to measure, not promised: parsing only the function being edited against what is kept of the rest, to
shorten the 1.7 s.  It is CppCompilerLib's binder; look before planning it.

Steps:
  1. Measure: the light path's cost and what it can't type, over a few hundred "." and "->" in the workspace; and
     try the parser on a text with the dummy name (3 above).
  2. The list and its popup (WindowLib: a chooser at the caret that the editor keeps typing through, whose rows can
     be added to while it is open, with a greyed "working" row), with keywords and the file's own names, so the
     keys, filtering, Enter and Tab can be checked before types are.
  3. The light path: what is in scope; members after ".", "->" and "::", with access; #include paths.
  4. The kept parse on the edits thread, the dummy name, and its results merged into an open list.
  5. Writing a function's brackets, and Parameter Info after it.

6. Automatic indenting, Tab, and the editor's other line commands: OPEN
-----------------------------------------------------------------------

What there is now (BaseLib's CTextEditing, so every text area; the keys in WindowLib's EditCommands.cpp):
  - Tab types spaces to the next tab stop; with lines selected it indents them (IndentLines), with spaces; in a box
    selection it types spaces.  Shift+Tab (BackTab) unindents the selected lines or the caret's: a tab, or up to a
    tab's worth of spaces.
  - Enter puts in a line feed and nothing else.
  - Duplicate (Control+D) and Delete Line (Control+Y) exist.  Control+Cursor Up and Down scroll.
  - There are no comment commands and nothing moves a line.

What to build (the user: Tab types a tab; spaces are no longer typed by Tab anywhere):
  1. Tab types a tab character, and IndentLines puts a tab at the start of each line.  BackTab is right already.
  2. Enter keeps the line's indent (its leading tabs and spaces, as they are); in a code editor, one tab more after
     a line that ends in "{", and a "}" typed on a line of only white space goes back one.  The first part in
     CTextEditing; the brace part in CCodeEditor or the IDE, as it is about C++.
  3. Comment with Line Comment (Control+/): the caret's line or the selected lines, // put in or taken out, the
     caret moving down a line when nothing is selected, as IntelliJ's.  Comment with Block Comment
     (Control+Shift+/): the selection.
  4. Move Line Up and Down.  IntelliJ's keys are Alt+Shift+Cursor Up and Down, which are taken here; its
     Control+Shift+Cursor Up and Down (Move Statement) are free, and are what this file planned.
  5. TestBaseLib (TestTextEditing) for 1 to 4, on the 65 targets too; the IDE's checks for the keys; editor.md.

DECIDED by the user, 2026-11-26: Tab in a box selection types a tab on each row, as everywhere else.  (Rows that
