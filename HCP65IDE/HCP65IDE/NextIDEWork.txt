2. Find and Replace in the file, and the regular expression engine
-----------------------------------------------------------------

What is missing: there is no Find or Replace within a file.  The only search is Find in Files (Ctrl+Shift+F,
CIDEFindInFiles) with its Current File scope.  Nothing in the code has a regular expression engine: BaseLib has none,
and std::regex isn't used.

The engine (the user: write it in BaseLib): CRegex, on CTextParser where it parses (use BaseLib's text parser, not
hand scanning).  The syntax IntelliJ's find takes (Java's, the same as ECMAScript's for what is used): classes and
ranges, groups and non-capturing groups, alternation, * + ? {n,m} greedy and lazy, ^ $ \b, \d \w \s and their
capitals, escapes; $1 and $0 in replacements; case-insensitive matching.  Compiled once to a backtracking matcher.
BaseLib is compiled for the W65C816 too, so keep to what BaseLib's own code does (no standard library, the narrowest
integers that fit).  Tested in TestBaseLib.

Find, as IntelliJ's: Ctrl+F opens a search bar over the editor (not a dialog), filled from the selection or the word
at the caret.  As the text is typed every match in the file is highlighted (CTextArea already highlights occurrences:
FindOccurrences, and the gutter's marks), the nearest is selected, and the bar says "3 of 17".  Enter or F3 goes to
the next, Shift+Enter or Shift+F3 to the previous, wrapping round.  Ticks for Match Case, Words and Regex, remembered
in Settings.  Escape closes it and leaves the caret on the match.  Ctrl+R opens it with a Replace field: Replace and
Replace All, each one undo (CTextArea::ReplaceRanges), with Regex's $1 groups.  "In selection" when the selection is
more than a line.

Where: a bar component above CIDEEditorTab's editor; the search itself on CTextDocument so other text areas can use
it.  Ctrl+F, Ctrl+R, F3 and Shift+F3 are free in the keymap.

5. Code completion, basic and smart
-----------------------------------

What is missing: no completion while typing.

When it opens (the user): by itself only straight after "." "->" and "::"; otherwise on Ctrl+Space (basic) or
Ctrl+Shift+Space (smart).  Not as an identifier is typed.

Basic, as IntelliJ's: a popup list of what can be written there, filtered as more is typed (camel humps: "GSN" finds
GetSelectedNode), each with its icon, its type or signature, and its class or namespace; Enter or Tab writes it (Tab
replaces the rest of the word), a function with its "(" and the caret between ")" when it takes arguments; parameter
info (Ctrl+P) after it.  What can be written comes from the code model (CCPPIndex, CIDECodeModel):
  - after "x." or "x->", the members of x's type, inherited ones too, by access from where the caret is;
  - after "N::", what N declares;
  - otherwise what is in scope: locals and parameters (the function's own syntax tree), the class's members, then
    the namespaces' and the globals';
  - #include "..." completes paths from the include directories; keywords too.

Smart (the user: build it with basic): only what has the type expected where the caret is, ranked first by how
close the type is: an argument (the parameter's type, from the call's overloads), the right of "=" (the left's type),
a return (the function's result), an initialiser (the variable's type), a case label (the switch's enum's
enumerators); with what converts (a derived class's pointer for a base's, an enum's enumerators for the enum).

The type of an expression is the hard part, and both need it: the index knows declarations, not expressions.  The
compiler's binder (CCPPBinder) works types out; Introduce Variable already asks the compiler for an expression's type
(compile check): see how, and whether it is quick enough for a keypress, or whether a lighter path through the index
is needed for "name.member" chains.  Measure on the ModPlay workspace: under about 100ms from the key to the popup.
CppCompilerLib is 3c's: ask it before changing the binder.

10. Reformat Code
-----------------

The user: wanted, as an item of its own after the others (2026-11-17).

What to build, as IntelliJ's Reformat Code (Ctrl+Alt+L, on the file or the selection, and from Solution Explorer on
a folder or project, with Optimise #includes as a tick): the code laid out in the house style.  The rules are what the
code already does; write them down from it before coding, and show them to the user:
  - indents in tabs; braces on lines of their own; one statement a line;
  - a function's locals declared at its top, their names lined up in a column with tabs; a class's fields and its
    member functions' names lined up the same way, a block at a time;
  - a ////// banner over each function in a .cpp, made if it is missing (the templates' Function Banner);
  - spaces round binary operators and after commas, none inside brackets;
  - comments and blank lines kept where they are; a line longer than it was is never made.
The proof: reformat each library of CommonLibraries in a scratch copy and look at the diff, which should be close to
nothing; each difference is either a rule to fix or a file that breaks the house style (list those for the user, and
don't commit a reformatted library without asking).  Settings: a page with the rules' few choices (the tab width for
lining up, the column banners go to) if the code turns out to vary.
