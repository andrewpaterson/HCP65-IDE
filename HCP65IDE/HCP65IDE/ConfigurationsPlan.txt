Where a configuration's settings are now (2026-11-25, before C0)
----------------------------------------------------------------

- MSVC: each .vcxproj, an <ItemDefinitionGroup> for each Configuration|Platform in its <ProjectConfigurations>.  No
  project imports a shared .props, so what every project has (/arch:AVX2, /fp:fast, /GS- and the rest) is written
  out in each of the 101 real .vcxproj files, for each configuration (CommonLibraries 47, HCP65 34, HCP65-IDE 15,
  LogiCim 5).  Of the 188 on disk, 35 are tests' Output copies (gitignored) and 52 are test fixtures (the IDE checks'
  Input, TestBuildLib's, TestIndexLib's and TestVisualStudioLib's Input), kept byte for byte and moved only where a
  test is about configurations.
- GCC from CMake: each test folder's CMakeLists.txt (37 of them).  They read their sources from the .vcxproj files
  (vcxproj_sources, a copy in each of 35 of them) and nothing else: their defines (LINUX_GNU, NDEBUG) and options
  (-fno-strict-aliasing, -fno-lifetime-dse, -m64/-m32, -march=haswell, the Release options) are written by hand, in
  baselib_options, in each copy.
- GCC from the IDE: CGCCBuild (BL/GCCBuild.cpp) compiles with the Release|x64 or Debug|x64 configuration's include
  directories and defines and nothing else.  The defines are MSVC's (_LIB, _CRT_SECURE_NO_DEPRECATE), LINUX_GNU isn't
  among them, and none of the options above are passed.  That is the EngineOutput failure (BaseLib/DebugOutput.h
  defines EngineOutput only for _MSC_VER, WIN_GNU_32, LINUX_GNU or __LIBC65__); with LINUX_GNU alone the code would
  build but could break when it runs (strict aliasing, lifetime DSE: see TestBaseLib's CMakeLists.txt).  Since C0
  (2026-11-27) CGCCBuild adds LINUX_GNU and those options itself on Linux.
- The HCP65 compiler: the solution's .hcp65build file (CBuildConfigurations, BL/BuildConfiguration.h): its toolchain,
  the solution configuration it takes includes and defines from (Solution="Release|Win32"), its compile options
  (NoFloats, MathTables, PreferSize, Debug, Unoptimised and the rest), what it links (<Image>, <Executable>, <Module>)
  and what debugging loads (<Load>, <Lines>, Card, CardPath, BreakpointSpace).  A solution without one gets
  configurations made up from its own (CBuildConfigurations::AddDefault, BL/BuildConfigurations.cpp: Debug|Win32
  gives Debug|W65C816, Debug|65C64 and Debug|GCC).
- The code index (IXL/WorkspaceIndex.cpp): the build configuration's solution configuration's defines, and
  AddCompilerDefines pretends to be MSVC (_MSC_VER, _WIN32, _M_IX86 or _M_X64) whatever the toolchain is.

So one configuration's settings are in up to four places, and the GCC ones are in a place (CMakeLists.txt) the IDE
never reads.


The idea
--------

Each .vcxproj also holds its GCC and HCP65 configurations, as ItemDefinitionGroups for their own
Configuration|Platform, the platform naming the toolchain and the target (GCC-x64, HCP65C816, HCP65C64: question 1):

  <ItemDefinitionGroup Condition="'$(Configuration)|$(Platform)'=='Release|GCC-x64'">
    <ClCompile>
      <PreprocessorDefinitions>NDEBUG;LINUX_GNU;%(PreprocessorDefinitions)</PreprocessorDefinitions>
      <AdditionalOptions>-O3 -m64 -march=haswell -fno-strict-aliasing -fno-lifetime-dse %(AdditionalOptions)</AdditionalOptions>
    </ClCompile>
  </ItemDefinitionGroup>
  <ItemDefinitionGroup Condition="'$(Configuration)|$(Platform)'=='Release|HCP65C816'">
    <ClCompile>
      <PreprocessorDefinitions>NDEBUG;%(PreprocessorDefinitions)</PreprocessorDefinitions>
    </ClCompile>
    <HCP65Compile>
      <NoFloats>true</NoFloats>
      <PreferSize>true</PreferSize>
    </HCP65Compile>
  </ItemDefinitionGroup>

- Visual Studio and MSBuild use only the groups whose condition is true for what they build, and no Visual Studio
  configuration is Release|GCC-x64, so these groups change nothing there.  They are not added to
  <ProjectConfigurations>: Visual Studio would list configurations it can't build.  Whether a .sln can list them is
  to be tried on Windows (question 1, trial W1); until then they aren't in it.
- What MSVC and GCC both have keeps MSVC's name: ClCompile's PreprocessorDefinitions, AdditionalIncludeDirectories
  and AdditionalOptions (for g++, its own arguments), Link's AdditionalOptions and AdditionalDependencies.  Only the
  HCP65 compiler's own options get tags of their own (HCP65Compile, named as the .hcp65build attributes are).
- What every project has goes in shared property sheets, each project importing its repository's by a path from
  the project (question 2; not from $(SolutionDir), which differs between the solutions a shared project like BaseLib
  is in, and not Directory.Build.props).  LINUX_GNU and the g++ options are written once, and MSVC's shared settings
  move there too.
- The .hcp65build file goes (question 3).  What a program links into (<Image>, <Executable>, <Module>) moves into
  its project, an HCP65Link group as MSVC's projects have Link.  What debugging needs (<Load>, <Lines>, Card,
  CardPath, BreakpointSpace) moves into run configurations, which can be shared (committed) as IntelliJ IDEA's are.
  Build configurations are then only names mapped to the projects' groups: the projects say what is built, run
  configurations how it is run.


What the projects share (surveyed 2026-11-25)
----------------------------------------------

The 101 real projects: 78 C++ projects (37 static libraries, 41 applications), 21 HCP65 Makefile projects (built by
hcp65build: Boot, Kernal, Init, Shell, Libc65, the 8 drivers and the test programs), Website and X65C64-Proposal (no
sources) and ExceptionsTest (no configurations).  98 have Debug and Release for Win32 and x64; HCP65IDE has
Reference|x64 too.  The survey script: each setting per configuration, how many projects set it, to what.

Not surveyed (found 2026-11-27, question 18): HCP65-Sculpt (3 projects, and 2 CMakeLists.txt with their own copies of
vcxproj_sources and baselib_options), WindowInputTester (1 and 1) and StarControlRedux (3 and 2) build CommonLibraries'
projects too.

Every C++ project has these, the same in each (to Common.props, by configuration):
  - Configuration: PlatformToolset v142, CharacterSet NotSet.
  - ClCompile, all: WarningLevel Level3, TreatWarningAsError, CallingConvention VectorCall, EnableEnhancedInstructionSet
    AVX2, FloatingPointModel Fast, MultiProcessorCompilation, OpenMPSupport, EnableParallelCodeGeneration,
    PrecompiledHeader NotUsing, FunctionLevelLinking.
  - ClCompile, Debug: Optimization Disabled, InlineFunctionExpansion Disabled, BasicRuntimeChecks EnableFastChecks,
    BrowseInformation, DebugInformationFormat EditAndContinue, RuntimeLibrary MultiThreadedDebugDLL, SDLCheck true,
    StringPooling false.
  - ClCompile, Release: InlineFunctionExpansion AnySuitable, IntrinsicFunctions, FavorSizeOrSpeed Speed,
    WholeProgramOptimization, BufferSecurityCheck false, DebugInformationFormat ProgramDatabase, RuntimeLibrary
    MultiThreadedDLL, SDLCheck false, StringPooling true.
  - _ProjectFileVersion.

Every application has these (Link; a static library ignores Link, so they can go in Common.props too):
  GenerateDebugInformation, ImageHasSafeExceptionHandlers false (Debug), EnableCOMDATFolding and OptimizeReferences
  (false Debug, true Release), LinkTimeCodeGeneration (Release), TargetMachine (MachineX86, MachineX64),
  LinkIncremental (true Debug, false Release), IgnoreSpecificDefaultLibraries empty, SubSystem Console (37; the 4
  window programs, HCP65Emulator, HCP65Tester, HCP65IDE and LogiCim, are Windows and keep it), AdditionalDependencies
  shlwapi.lib (all 41; ws2_32, winmm, dinput8, dxguid and xinput added by the 7 that need them).

Most share, the rest add to it:
  - PreprocessorDefinitions: Debug _DEBUG;_LIB;_CRT_SECURE_NO_DEPRECATE;DEBUG;BREAK_ON_WARNING;BREAK_ON_ERROR (63-67
    of 78), Release NDEBUG;_LIB;_CRT_SECURE_NO_DEPRECATE (69-73).  The window libraries and programs add
    WIN32;_WINDOWS (and D3D_DEBUG_INFO in Debug); StandardLib adds DEBUG_POINTER; EmulatorDebugLib, KicadLib and
    ThreadLib leave out DEBUG; WinRefLib leaves out _LIB and BREAK_ON_*.  Applications define _LIB too.
  - IncludePath: 16 different values, but all are the same roots at different depths (CommonLibraries\Libraries,
    HCP65\Libraries, the repository's Libraries) and a few extras ($(VULKAN_SDK)\Include, $(SolutionDir)).  The
    sheets define $(CommonLibrariesDir) and $(HCP65Dir) from $(MSBuildThisFileDirectory), each repository's sheet
    sets the IncludePath its projects have, and a project keeps only its extras.
  - The HCP65 Makefile projects share only NMakeIncludeSearchPath (and its copy in ClCompile's
    AdditionalIncludeDirectories): 5 values, the same roots at different depths.  Programs:
    UserLib;CommonLibraries\Libraries;HCP65\Libraries; drivers: Kernal;CommonLibraries\Libraries;HCP65\Libraries.
    Into HCP65.props as two properties.  Their compile options are the .hcp65build file's (C4).

Settings that differ for no reason seen (drift).  A sheet makes them one; each is the user's (question 8):
  - ExceptionHandling: false in most, unset (so /EHsc, exceptions on) in 4 to 19 projects depending on the
    configuration, and sometimes only in some of a project's configurations (EmulatorDebugLib, KicadLib, ThreadLib:
    false in Debug, unset in Release).  Turning it off where it is on breaks a project that uses try or throw.
  - DisableSpecificWarnings (code analysis's C26xxx warnings only): 26440;26447;26455;26476, 26440;26447;26455, or
    unset, varying by project and configuration.
  - FloatingPointExceptions false in 21-42 projects; the rest unset (the default is the same, off).
  - Optimization MaxSpeed set in 16 Release projects; unset in the rest (Release's default is MaxSpeed: the same).
  - Configuration's WholeProgramOptimization true in 35 Release projects; the others have only ClCompile's.
  - EnableASAN false in 21-30, Bscmake PreserveSbr in 26-31, CodeAnalysisRuleSet AllRules.ruleset in 64-68.
  - TestInputLib's Release is Unicode (CharacterSet), its Debug NotSet.
  - TestBaseLib, TestEmulatorDebugLib and TestThreadLib link incrementally in Release.
  - 43 projects import Microsoft.CPP.UpgradeFromVC70.props (left from converting a Visual Studio 2003 project); the
    others don't.
  - Win32 OutDir/IntDir set in 22 projects ($(SolutionDir)$(Configuration)\), x64's in 9 of those 22.

So a typical C++ project's four ItemDefinitionGroups (about 25 settings each) and its configuration PropertyGroups
come down to its include extras, its added defines and libraries, its SubSystem if Windows, and ConfigurationType.

Stages
------

The names are question 1's (Release|GCC-x64, Release|HCP65C816, Release|HCP65C64, and the solutions' Release|MSVC-x64),
which C11 brings in; until it is built the build configurations are still Release|GCC, Release|W65C816 and
Release|65C64, as C0's text has them.

C0. A stopgap: CGCCBuild adds the Linux options itself (question 7)
  C0-1. On Linux, CGCCBuild::AddCompile adds -DLINUX_GNU and baselib_options' compile options (-m64, -march=haswell,
     -fno-strict-aliasing, -Wno-ignored-attributes and the other -Wno- options; Release: -O3, -ffunction-sections,
     -fdata-sections, -fno-stack-protector, -U_FORTIFY_SOURCE, -fno-lifetime-dse, -fno-math-errno,
     -fno-trapping-math; Debug: -g) after the project's defines; the link adds -m64 (and Release --gc-sections).
     One list in GCCBuild.cpp, its comment naming TestBaseLib's CMakeLists.txt as where it came from.
  C0-2. Tests: TestBuildLib's GCC command test expects them; the IDE builds TestBaseLib's Release|GCC and it runs and
     passes.  C7-4 removes the list when every repository's projects have their GCC-x64 groups (2026-11-27: not C3-2).
  Built 2026-11-27 (the user: "add C0 too"): the lists are in GCCBuild.cpp under LINUX_GNU, Debug being a solution
  configuration named Debug|...; TestBuildGCC (Debug) and TestBuildGCCRelease (Tools, compiles and links) check them.
  Not -Wall -Wextra or -flto, which CMake also passes.  On the way: a GCC application was linked to
  Output\GCC\<configuration>\<project>, its own objects' folder without Windows' .exe, so no GCC application linked
  on Linux; objects are now in Output\GCC\<configuration>\Objects\<project>\.  The five programs' mains became

  WinInputLib) and not X11Lib, which a GCC build on Linux needs (C10).

C1. VisualStudioLib reads the GCC and HCP65 groups
  C1-1. CVcxProject (VSL/VcxProject.cpp) keeps a configuration for each group whose platform is a toolchain's name,
     as well as those in <ProjectConfigurations>.  Now SetProperty drops a group for a configuration that isn't
     listed.  Such a configuration is marked as not Visual Studio's (MSVC never builds it).  The conditions read
     (2026-11-27): '$(Configuration)|$(Platform)'=='X|Y' as now, and '$(Configuration)'=='X' or '$(Platform)'=='Y'
     alone, each setting every configuration it is true of.  Any other condition is false, and the sheets are written
     with these three only.  (GetVcxConditionConfiguration now takes whatever follows ==' for a whole name, so a
     sheet's '$(Configuration)'=='Debug' would set nothing.)
  C1-2. Per tool reads: AdditionalOptions (ClCompile and Link) as an argument list, split as a command line is
     (quotes kept), %(AdditionalOptions) as PreprocessorDefinitions' %(...) is now; the HCP65Compile tags as named
     properties.
  C1-3. Tests: TestVisualStudioLib reads a project with Release|GCC-x64 and Release|HCP65C816 groups and none in
     <ProjectConfigurations>: their defines, options and HCP65 properties, and that Release|Win32 is unchanged.
  C1-4. (2026-11-27) What a toolchain's configuration takes from the project as a whole: its ConfigurationType (the
     same in all four configurations of each of the 109 projects) and its include directories.  Both are written in
     groups conditioned for each MSVC configuration now, so a configuration made from a GCC-x64 group alone has
     neither, and CBuild::GetProjects takes a project with no ConfigurationType for an application: every library
     would be linked as a program.  Where they come from is question 15.

C2. VisualStudioLib follows imports
  C2-1. <Import Project="..."/> of a .props file: its PropertyGroups and ItemDefinitionGroups are read where the
     import is, so a project's own group after it adds to or replaces what the sheet set, as MSBuild has it.  The
     projects import in an ImportGroup conditioned for one MSVC configuration (question 2: once per configuration),
     which is never true for Release|GCC-x64: how a toolchain's configuration imports the sheet is question 16
     (2026-11-27).  Paths
     with $(SolutionDir), $(ProjectDir) and $(MSBuildThisFileDirectory); an import whose Condition is
     Exists('...').  Directory.Build.props isn't read: question 2 chose imports by path, and nothing would use it
     (2026-11-27).  Microsoft's own imports ($(VCTargetsPath), $(UserRootDir)) are skipped as now.
  C2-2. Opening a solution watches the imported sheets as it watches its projects: a changed sheet reloads the
     projects that import it.
  C2-3. Tests: a project importing a sheet that sets defines and options for Release|GCC-x64, and adding its own; a
     sheet importing another; each condition C2-1 reads, and one it doesn't.

C3. GCC builds with the project's GCC configuration
  C3-1. A GCC build configuration's solution configuration is the GCC one (Solution="Release|GCC-x64") when the projects
     have it; CBuildConfigurations::AddDefault prefers it to Release|x64.  A project without a GCC group builds as now
     (x64's include directories and defines, and C0's list), and the build says once which projects those are.
  C3-2. CGCCBuild::AddCompile passes ClCompile's AdditionalOptions after the -D arguments; the link passes Link's
     AdditionalOptions and AdditionalDependencies, a name with no path or extension as -l<name> (X11 is -lX11), any

     given twice; one without keeps the list until C7-4.  (2026-11-27: this step used to take C0's list out, but no
     real project has a GCC group before its repository's C7, so every GCC build would have lost LINUX_GNU again in

  C3-3. Tests: TestBuildLib's GCC build test project gets a GCC group with a define only it has and an option
     (-fno-strict-aliasing); the test asserts both are in the compile command.  IDE: a check builds TestBaseLib's
     Release|GCC-x64 and runs it.

C4. HCP65 compiles with the project's HCP65 configuration
  C4-1. An HCP65 build configuration's defines and include directories come from the project's HCP65C816 or
     HCP65C64 group when it has one (Solution="Release|HCP65C816"), from Win32 as now when it hasn't.
  C4-2. Its compile options (NoFloats, MathTables, PreferSize, WarnMissingOverride, Exceptions, KeepUnusedObjects,

     Shell" becomes those projects' own setting.
  C4-3. Linking: a program's <Image>, <Executable> or <Module> (with its Region and Symbol rows) is read from its
     project's HCP65Link group (the startup project's, as CHCP65Build links now), in a group with no condition or a
     configuration's.  Debug and Release share it instead of repeating it.
  C4-4. Edit Build Configurations (IDE/IDEBuildConfigurationsDialog.cpp) shows the compile and link options read from
     the projects, and edits them (question 5, C9).  Its card, load, lines and breakpoint fields go to Run Configurations
     (C8).
  C4-5. The 20 HCP65 solutions' .hcp65build files (HCP65/**/HCP65*.hcp65build) are moved: compile options into
     their projects' HCP65Compile groups, linking into HCP65Link, debugging into shared run configurations (C8).  An

  C4-6. Tests: TestBuildLib builds an HCP65 test solution whose options are only in its projects and gets the same

  C8-3. Run Configurations (IDE/IDERunConfigurationsDialog.cpp) gets the HCP65 Emulator fields and IntelliJ's "Store

  C8-4. Debugging (IDE/IDEDebugging.cpp, IDEDebugger.cpp, IDEListingSource.cpp) reads the card, loads, lines and

  C9-4. After a write the projects are read again (C2-2 watches the sheets), and an open solution in Visual Studio

  C9-5. Tests: TestVisualStudioLib sets, overrides and removes a property in a project and a sheet, and compares the
