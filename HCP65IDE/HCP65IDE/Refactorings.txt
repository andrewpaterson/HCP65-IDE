Refactorings in the HCP65 IDE (plan, 2026-11-14)
================================================

The intent (the user, 2026-11-14): the IDE makes refactorings to C++ in the same way that IntelliJ IDEA can to Java
code.  IntelliJ IDEA is the reference for what each refactoring does and for its key, as for the rest of the IDE.
Each refactoring is an item of its own, checked by running the IDE.  The order is proposed, not agreed: the user
picks what is built next.

No half-measures (the user, 2026-11-14: "The aim is to make the HCP65 fully useful").  Each refactoring is built to
what IntelliJ's does, with its dialog, its preview and its conflicts: the lines below name them, they don't size
them.  One of them is the work Rename was, or more: Change Signature alone is its table of parameters, every call's
arguments rewritten, the conflicts found before anything changes, and the assembly's labels.  A refactoring is built
in steps that are each checked and committed, and the steps add up to all of it.

Templates are a large part of this code (the user, 2026-11-14), so they are planned for from the start and are not a
limit: every refactoring says what it does in a template, and what templates need comes before the refactorings that
need it.  Planned again for that on 2026-11-14.

Done before this plan: Rename (Shift+F6, IDERename.cpp), in hand written assembly too (IDERenameAssembly.cpp), and
Rename File (IDEFileRename.cpp, RenameFile.txt).  The editor's Refactor menu has them and a disabled
"Extract Method...".

Progress is at the end ("Where it is"); what the user is asked is in RefactoringQuestions.txt.


Templates
---------

A template's body isn't code until it has arguments, and a refactoring has to know what each name in it means and
what type each expression has in the template's own words (M*, not CFoo*).  There are three kinds of name in one:
  a. Names that don't depend on the arguments: size i, miUsedElements, memcpy.  The same in every instance.
  b. Names that depend on the template's own shape: M* pv = Get(i), mcArray.Add(x) where mcArray is a
     CArrayTemplate<M>.  The type can be said in the template's words and the member found in the template.
  c. Names only an instance decides: pv->Init(), Compare(a, b) with arguments of M.  They can be different things
     in different instances.

What others do (looked up 2026-11-14): clangd guesses in the template as written (its HeuristicResolver: the
member is looked up in the primary template, specialisations ignored, "results may not be fully accurate");
ReSharper C++'s older documentation says every name in a template is treated as dependent; Visual Studio lets the
user name sample arguments for a template and analyses that instance; Google's ClangMR refactors from the instances
and merges the edits, leaving what is right for one instance and wrong for another to a person.  Nobody has it
whole.  The two real ways are the template as itself and the instances as evidence, and this plan has both: the
compiler is ours, so the first is the type checker's own work and not a guesser beside it.

  T1. Every instance is evidence (kind c).  A name in a template's body is a reference of what it resolves to in
      each instance, in whichever unit the instance is, so Find Usages and Rename of CFoo::Init have mp->Init() in
      CHolder<M>.  Done 2026-11-14: instances in other units than the one that indexed the header were already
      kept (CCPPIndex::Gather keeps resolved names in files another unit indexed); two instances in one unit kept
      only the first's, and now keep each (SCPPResolvedName's iNext, CCPPSemanticPass::GetNextResolved).
      TestCppIndexTemplateInstances.
  T2. Families (kind c).  mp->Init() in CHolder<M> ties together every class CHolder is instantiated with: an
      interface nobody wrote.  Changing CFoo::Init alone breaks CHolder<CBar>.  So a refactoring that changes a
      member a template's body names shows the family as a conflict: "CHolder<M> calls this as mp->Init(), which is
      also CBar::Init and CBaz::Init: change them all, or cancel", as a virtual function's overrides are changed
      together.  Done for Rename 2026-11-14 (it renamed the template's mp->Init() with CFoo::Init and left
      CBar::Init): a reference a template's instance resolved is flagged CPPIF_INSTANCE, CCPPIndex::FindFamily
      gives the symbols that share such a place, and CIDECodeModel::FindRenameTarget takes a symbol's overrides and
      family, and theirs.  Each later refactoring that changes how a member is named or called does the same.
  T3. The template as itself (kinds a and b).  The type checker checks a template's body once with each parameter
      bound to a type that stands for itself and is written by its name: the types are M*, CArrayTemplate<M>&, as
      the source has them; a member of CArrayTemplate<M> is found in the template; what only an instance decides
      has a dependent type, which what is made of it has too, with no error.  A template nothing instantiates is
      typed like any other.  The kept check's GetType answers with these in a template's body, never with an
      instance's types.
      Done 2026-11-14 in the type checker's own way: the template is instantiated as itself, each type parameter a
      placeholder class with nothing in it that is written as its name (CCPPUnit::PlaceholderClass,
      CheckTemplatesAsThemselves), and its functions checked quietly.  What only an argument would have isn't
      there to find, so such an expression has no type (GetType is NULL) where this plan said "a dependent
      type": a refactoring says its type depends on the template's arguments.  An instance with arguments no
      longer gives its types to the pass.  Left: a partial specialisation isn't checked as itself; a value
      parameter is 1 in the check (question 6); the index's checks don't do it (question 5).
  T4. What a refactoring writes in a template.  A member of a class template defined outside it is
      template<class M> void CArrayTemplate<M>::Name(...), in the header and not a .cpp; a function made from part
      of a function template has the parameters it uses; typename where a dependent type needs it.  Part of each
      refactoring that writes a declaration.
  T5. Specialisations.  A template and its explicit and partial specialisations are definitions of their own with
      one name: Rename, Change Signature and Safe Delete take them together, as T2's families.
  T6. Classes a macro makes (ARRAY_BLOCK making CArrayBlock and CArrayLargeBlock from one text included twice) are
      templates in what they do and macros in what they are: none of the above reaches them, and code a macro made
      has no source of its own.  Done 2026-11-15, by making BaseLib's real templates (RefactoringQuestions.txt 48;
      CommonLibraries' ArrayTemplatesPlan.txt): CArrayBlockBase<SIZE>, CArrayTemplateBase<M, BLOCK>,
      CArrayTemplatePrimitiveBase<M, TEMPLATE>, CArrayCharBase<PRIMITIVE> and CCharsBase<STRING, TEXT>, their old
      names kept by classes deriving from them.  The refactorings meet them as any other templates.  Nothing was
      built for macro-made classes; one written elsewhere still has no source of its own.


Foundations
-----------

Exists:
  - The index (CCPPIndex: every name's declarations, definitions and uses, a local's too, each use read, written or
    called, in its class or function; base classes and virtuals), Find Usages, edits to many files as one undo
    group, and "nothing changes if a file changed since it was indexed".
  - The syntax tree, each node with the source it was parsed from, names with the symbol the parser resolved, and
    scopes to look a new name up in for a clash (CCPPScope::Find and FindHere).
  - The kept check (CommonLibraries ecab9f7fd and eb887e04d, 2026-11-14).  CCPPSemanticPass::Check with bKeep keeps
    the checked unit until the pass is killed: GetType gives any expression's type, AppendType and AppendDeclaration
    write a type as C++ (CCPPTypeWriter), and FindChanges says how the variable a name names is changed where it is
    used (assigned, bound to a reference that isn't const, its address taken, a member function that isn't const
    called on it).  The index's checks aren't kept.

To build:
  F1. The checked unit in the IDE.  CIDECodeModel makes a kept check of one file when a refactoring starts (a header
      in a unit that includes it, as the edited files are parsed), and finds the node of a selection or of the
      caret.  Done 2026-11-14 as CIDERefactorUnit (IDERefactorUnit.h): Parse, with the kept check if asked,
      FindTokenAt, FindNodeAt, FindNodeOfTokens, GetRange.  Safe Delete uses it without the check; nothing has
      used the check yet.
  F2. Declared type text.  A variable's or a function's type copied from its declaration, so uint32 and size stay
      what they are: the compiler's types have no typedefs in them, and the type writer writes size as
      "unsigned long long".  The type writer is for an expression that is computed.  In a template the declaration's
      text is already in the template's words.  With Introduce Variable.
      Done 2026-11-14: CIDERefactorUnit::AppendDeclaredType, for a variable, a parameter or a field named and for
      a call (what its function is declared to return).  A type that names a template's parameter, or something
      declared in a class, is left to the type writer: it may not mean the same where it is to be written.
  F3. Flow over the syntax tree.  Which locals a selection reads, writes and leaves live after it, and where it
      exits (return, break, continue, goto).  The compiler's liveness is the IR's, which a check doesn't make; this
      is the syntax's, and says more is live than is where it can't tell.  It is the same in a template.  With
      Extract Method.
  F4. Preview and conflicts.  IntelliJ's "problems detected" list before anything changes, and one undo for the
      whole refactoring.  T2's families are its first conflict.  With T2.
  F5. A declaration and its definition as one thing: a member's declaration in the header and its definition in the
      .cpp, found from either; a class template's member defined outside it, in the header (T4).  With Change
      Signature.


Phase 1 - nothing new from the compiler
---------------------------------------

  1. Safe Delete (Alt+Delete).  A symbol is deleted only if Find Usages finds no use of it; otherwise the usages
     are shown.  Its declaration and its definition go together.
     In a template: a member a template's body names through an instance is used (T1); a member of a template
     nothing instantiates has only the uses the parser found, and says so.
     Done 2026-11-14 (IDESafeDelete.h says what it does), but for:
       - a class's files: a class taken out leaves its .h and .cpp with their #includes and guards, and the
         projects' items and the #includes of the header; IntelliJ deletes a class's file with it;
       - Safe Delete of a file from Solution Explorer;
       - a member of a template nothing instantiates doesn't say its uses may be incomplete;
       - a parameter (it is Change Signature's, and is refused until that is done).
  2. Change Signature (Ctrl+F6).  Parameters added, removed, reordered and renamed, and the return type changed, in
     the declaration, the definition, every override and every call.  A new parameter has a value for the calls
     there already are.
     In a template: a member of a class template changes in the template and at every call on any instance; a
     function a template's body calls through an instance changes with its family (T2), the call in the body once;
     specialisations with the template (T5).
     Done 2026-11-14 (IDEChangeSignature.h says what it does), with its conflicts shown before anything changes
     (F4, for it: Problems Detected), a parameter's type and default value, the return type, the name (by
     Rename), and the assembly's labels asked of the compiler.  But for:
       - a constructor's calls that aren't written as calls (question 13);
       - specialisations (T5): an explicit specialisation of a function template is another symbol to the index,
         and isn't changed with the template;
       - a function type elsewhere that the function is assigned to (a pointer to it) is left, and said.
  3. Move:
       - a member function's body between the class (inline) and the .cpp;
       - Pull Members Up and Push Members Down;
       - a class to its own .h and .cpp, the #includes and the projects' files changed as Rename File changes them;
       - a function or a global to another file or namespace.
     In a template: a class template's member moves between the class and outside it in the header (T4), never to
     a .cpp; Pull Up to a base that is a template's instance, and out of a template to a base that isn't one, only
     for members that don't use the parameters.
     The first is done, 2026-11-15: Move Definition out of Class and into Class (IDEDefinitions.h says what they
     do), a class template's member too.
     Pull Members Up and Push Members Down are done, 2026-11-15 (IDEMoveMembers.h says what they do): functions
     and fields, static ones too, to any base class or to the deriving classes, a function up or kept abstract,
     with what stands in the way shown first.  Where either class is a class template a function defined outside
     goes with its body in the class.  But for:
       - the #includes the class a member goes to then needs (15);
       - nested types and enums of the class, which aren't offered;
       - a member's use of the source template's parameters isn't checked where it goes to a class that isn't
         that template's.
     A class to its own .h and .cpp is done, 2026-11-15: Move Class to Its Own Files (F6; IDEMoveClass.h says what
     it does), a class template with what its header defines outside it.  But for:
       - a class whose members are defined in more than one source file (Preprocessor_Linux.cpp and
         Preprocessor_Windows.cpp), which is refused;
       - a class and the rest of its header that each name the other, which is refused: one of them would have
         to be declared ahead (a forward declaration) for it, which 15 will know how to do;
       - a source file the class was all of is left with only its #includes;
       - undo leaves the new files there, empty (question 22).
     A function or a global to another file is done, 2026-11-15: Move to File, the same F6 (IDEMoveClass.h).  But
     for:
       - another namespace (question 26), and a function that is in one;
       - a static function, which only its file can use, is refused;
       - it goes to a header that is there: no new file is made for it.
  4. Copy (F5).  A class and its files under a new name.  A class template the same.
     Done 2026-11-15: Copy Class (IDEMoveClass.h), by what makes Move Class's files.  No key (question 27).


Phase 2 - the kept check
------------------------

These write a type, so in a template they need T3.

  5. Introduce Variable (Ctrl+Alt+V).  The selected expression becomes a local, every occurrence of the same
     expression in the function replaced if asked.  It is declared at the top of the function, as the house style
     has locals.
     In a template: declared in the template's words (M* pv); an expression whose type only an instance decides is
     refused, with why.
     Done 2026-11-14 (IDEIntroduceVariable.h says what it does), with the popup of the expressions at the caret
     when nothing is selected.  Questions 7 to 9 are about it.
  6. Inline Variable (Ctrl+Alt+N).  Refused if the variable is changed after its initialiser, or its initialiser
     has side effects.
     In a template: a call through an instance (pv->Next()) is taken to change what it is called on unless every
     instance's function is const.
     Done 2026-11-15 (IDEInlineVariable.h says what it does): a function's own variable with one value, given by
     its declaration or by the one statement that assigns it.  How each use changes it is the compiler's answer
     (CCPPSemanticPass::FindChanges, which is where the template rule is).  A value with side effects isn't
     refused outright: it is inlined where it is used once, and a conflict to continue past where it would be
     done more than once or not at all (question 28).  Not constants and fields (question 29).
  7. Introduce Field (Ctrl+Alt+F), Constant (Ctrl+Alt+C) and Parameter (Ctrl+Alt+P).  The same extraction to
     another place; Parameter is a Change Signature too.
     Done 2026-11-15, as kinds of Introduce Variable (IDEIntroduceVariable.h says what each does): a field in the
     class, after its last field; a constant as a #define, which is how constants are written here; a parameter
     by Change Signature, with the occurrences replaced in the same edit.  In a class template the field's type
     is in the template's own words, as the variable's is (T3).
  8. Introduce Typedef.  The selected type is given a name, and the other uses of the type replaced.  In a
     template it may be a typedef of the class template's, written with its parameters.
     Done 2026-11-15 (Ctrl+Alt+K; IDEIntroduceTypedef.h says what it does): in the file, in a class template (a
     member typedef) or in a template's function (its own), by where the template's parameters it names can be
     seen.  But for the other files that include a header a typedef is written in (question 33).


Phase 3 - flow
--------------

  9. Extract Method (Ctrl+Alt+M).  The selected statements, or expression, become a function.  The locals it reads
     are parameters; one local live after it is what it returns, more are reference or pointer parameters.  In a
     member function the declaration goes in the class and the definition in the .cpp.  Refused if the selection
     has more than one kind of exit.
     In a template: the parameters' types are their declarations' text (F2); a member of a class template is
     declared in the class and defined in the header as T4 writes it; from a function template the new function
     is a template of the parameters the selection uses.
     Done 2026-11-15 (Ctrl+Alt+M; IDEExtractMethod.h says what it does, and what F3 is: which variables the
     selection reads, changes and leaves used after it, by the syntax and the compiler's FindChanges).  From a
     function template the new function has all of that template's parameters, and the call names them.  But
     for: duplicates of the selection elsewhere; pointers in place of references (question 35).
 10. Inline Function (Ctrl+Alt+N on a function).  At one call or at all of them, the function deleted if asked.
     Refused for a virtual or recursive function, and for a body with several returns where a statement is.
     In a template: a class template's member inlined into another of its members stays in the template's words;
     into code outside, its parameters are the instance's arguments there.
     Done 2026-11-15 (the same Ctrl+Alt+N; IDEInlineFunction.h says what it does), on what Change Signature finds
     of a function.  A function with statements is inlined where its call is a statement, or all of what one
     assigns or returns; elsewhere the call stays and is said.  Also refused: one that changes a parameter, and a
     function template (a class template's member is done).
 11. Extract Superclass, Extract Interface and Extract Class (members moved into a new class held as a field).
     Built on Move and Introduce Field.  From a class template the new class is one too if what moves uses the
     parameters.
     Done 2026-11-15 (IDEExtractClass.h says what each does), on Pull Members Up's reading of a class's members
     and Move Class's making of files.  But for the "abstract" tick in the dialog (question 41), and an Init for
     an extracted class (question 42).
 12. Encapsulate Field.  A getter and a setter, the reads and writes replaced: FindChanges tells them apart.
     Done 2026-11-15 (IDEEncapsulateField.h says what it does).  A place that uses the field in a way neither
     stands for (its address taken, a reference bound to it) stays and is a conflict if the field is to be
     protected.


Phase 4 - C++ only
------------------

IntelliJ has none of these for Java.

 13. Generate a definition from a declaration, and a declaration from a definition; a declaration brought back in
     step with its edited definition.  Small once F5 is there.  A class template's member by T4.
     Generate Definition (Ctrl+Shift+D) and Generate Declaration are done, 2026-11-15 (IDEDefinitions.h): a member
     defined that its class doesn't declare is declared from the file as it is written, since the compiler has no
     symbol for it.  The two are brought back into step by the same commands: on a member's edited definition,
     Generate Declaration changes the declaration the class still has of that name (one that nothing defines) to
     match it; on an edited declaration, Generate Definition changes the definition it had.  With overloads of
     the name left undefined it can't tell which, and makes a new one.
 14. A function made inline in its header, or moved out to the source, static and inline put right.
     Done 2026-11-15, as Move Definition into Class and out of Class on a function outside any class.  What its
     body needs #included isn't looked at until 15: a function moved into its header may name what only the
     source file #includes.
 15. #includes added, removed and sorted: the #include a name newly used needs is added, those no name comes from
     removed, and an #include replaced by a forward declaration where only a pointer or reference is used.  A name
     a template's body uses through an instance needs the #include where the instance is, not in the template.
     Done 2026-11-15 (IDEIncludes.h says what it does): Optimise #includes (Ctrl+Alt+O) and Sort #includes, for
     the file in the editor.  What a file needs is the index's answer (CIDECodeModel::FindNeeds); which #include
     brings it is read from the files' texts (CIDEIncludeGraph); macros are read from the texts too, the index
     having none.  The file is checked as it would be before anything is changed, and an #include it doesn't
     compile without stays.  Left: the compiler's own headers aren't followed, so <> #includes are never touched
     and a header's #include that brings one to its includers stays; a class template is never forward declared;
     the files given an #include aren't checked themselves (only the file's own unit is); not tried yet on a
     solution the size of the libraries.
 16. Convert macro.  A #define of a constant to a const or an enumerator; a function-like macro to an inline
     function (a function template where its arguments' types differ between its uses) where each of its
     arguments is used once.  Inline macro, at one use.  With T6.
     Done 2026-11-15 but for T6 (IDEConvertMacro.h says what it does): Convert Macro... and, on a macro's name,
     Inline... (Ctrl+Alt+N).  A macro isn't in the index: its #define and uses are found by its name in the
     solution's files' texts.  Types are the compiler's, from kept checks: a constant's of its value written as an
     expression where the #define is, a function's parameters' and result's of the tokens each use made
     (CIDERefactorUnit::FindExpansionTokens, FindSpelledTokens: a macro's arguments are ordinary tokens of the
     file, wherever its body put them).  An argument used more than once is allowed, against the plan's "used
     once": a use where it does something is a conflict shown first.  The files are checked as they would be and
     must have no more errors.  Left: T6 (question 48); a macro #defined more than once or in the compiler's own
     headers; variadic macros (inlined, not converted); the first 30 files that use a macro are the ones checked.
 17. . to -> and back; a pointer parameter to a reference and back, every use and call changed.
     Done 2026-11-15 (IDEConvertPointer.h says what it does): Convert Pointer to Reference and Convert Reference
     to Pointer, for a parameter (its function's every declaration and override, from
     CIDEChangeSignature::FindSignature) or a local variable declared with its value.  The files changed are
     checked as they would be (CIDEFileEdits::CountErrors) and nothing is done if they have more errors.  Left: a
     field; a "* const"; the name keeps its prefix (question 50).
 18. Make a member function const (and static), its overrides with it, checked against what it changes; its family
     with it where a template's body calls it (T2).
 19. A function to a member function and back: its first parameter is this.
     Done 2026-11-15 (IDEConvertMember.h says what it does): Convert Function to Member Function and Convert
     Member Function to Function.  Left: a class template's member; the files that
     call it aren't given the class's #include if they only had its forward declaration (the check refuses, if
     the checker sees it: question 52).
 20. Extract template parameter: a type used in a function or class becomes a parameter.  A typedef of the
     template with the type it had keeps the code that used it compiling (the ACCU article "Refactoring Towards
     Seams in C++").  Its inverse: a parameter every instance gives the same argument is removed.
     The function's half done 2026-11-15 (IDETemplateParameter.h says what it does): Extract Template
     Parameter... on a type in a function, which becomes a function template; a definition in a source file goes
     to the header that declares it.  The class's half done too: on a type a class's field has, the class
     becomes a template of another name, its members' definitions come to its header, and a typedef of it with
     the type it had is its old name.  The inverse done too: Remove Template Parameter, for a class template's
     parameter that every use gives one argument.  Still to do: a function or a class that is a template already
     (another parameter added), a class declared ahead of its definition
     (its forward declarations would have to become the template's and the typedef), the inverse for a function
     template (its arguments aren't written at its calls: the compiler's instances would have to say them), and
     a template made a class again by it has its members inline in its header, not back in a source file.
 21. Move into or out of a namespace; a using added or removed, the names qualified or not to match.
     Planned 2026-11-16, once the compiler's namespaces were to the standard (CppCompilerLib's Part B stage 10, master
     5ae3e2ba8), at the user's word ("carry on with your refactoring"); questions 60 to 63 are what I assumed:
       a. Move to Namespace... (Refactor menu, Alt+Enter on its name; no key, as IntelliJ has none): a class, struct or
          union, an enum, a typedef or alias, a function, a variable, a class or function template, and a namespace
          itself, from wherever it is to another namespace, a new one, or the global namespace.  The dialog's field
          completes over the solution's namespaces ("A::B"; empty or "::" is the global namespace).
       b. All of it moves: its definition, every other declaration of it (forward declarations, prototypes, an
          extern, a friend's declaration is left), its explicit specialisations, and for a class its members'
          definitions outside it.  In each file the text stays where it is: the old namespace's block is closed
          before it and opened again after it, and the new namespace's is opened round it (namespace A { namespace B
          { for A::B, as C++14 writes it); next to a block of the new namespace it goes into that block instead, and
          a block left empty goes.  A definition written outside its namespace (int Old::F(void) { }) only has its
          name's qualifier changed.  A block made is written as the file's other blocks are, or as the house style
          (Aardvark.cpp): the brace on a line of its own, the body a tab in.  What moves is indented as its new block
          is.
       c. Every use is made to name it from where it is (the index's references, as Rename finds them): a use in the
          new namespace or one inside it, or where a using-directive of it is, is unqualified; any other is written
          with the new namespace's name (::Name for the global namespace where something nearer would hide it).
          A qualifier that named the old namespace is replaced; Old::X::Member keeps its ::X::Member.  A
          using-declaration of it (using Old::X;) names the new namespace, or goes where it isn't needed any more.
          With the dialog's "Add using-declarations" ticked, a file whose uses would all be qualified gets one
          using New::X; after its #includes instead, and its uses are left as they are.
       d. What moves names things of the namespace it leaves without their namespace (it found them by being in
          it): each of those is qualified, unless the new namespace is inside the old one.
       e. Problems Detected first, as Move's: the new namespace has something of the name already; a use whose new
          name something else would hide; functions and operators of the old namespace that take the class, which
          calls found through the class's namespace (argument dependent lookup) won't find any more.
       f. The labels that change (a namespace is part of a mangled name) change in hand written assembly too, as
          Rename changes them (RenameAssemblyOf).
       g. Move to File takes a function or a variable that is in a namespace (question 26): it goes into a block of
          its namespace in the header it goes to.
       h. The leftovers of 19 and 20 that are namespaces': Convert Function to Member Function of a function in a
          namespace, and Extract Template Parameter of a type written with its namespace.
     Checks for each, on Input/Namespaces (a solution of classes, functions, templates and assembly in namespaces).
     Built 2026-11-16 (CIDEMoveNamespace, IDEMoveNamespace.h says what it does): a to e, for a class (its members'
     definitions in the old namespace's blocks with it), enum, typedef, function, variable and template; a block it is
     alone in goes, one it starts or ends goes before or after it, a neighbouring block of the new namespace takes it,
     otherwise the old block is split round it; a use is named from its namespace or a namespace one of its file's
     using-directives opens, whichever is shorter.  Checks move-namespace-class, -function, -global, -nested,
     -usings, -conflict, -refused and -dialog on Input/Namespaces.  A declaration that a longer qualified name puts
     out of line with the ones round it isn't lined up again (Rename doesn't either).
