The navigation plan: in a file, between files, symbols, and the search dialogs and results (2026-11-20)
======================================================================================================

Navigation.txt lists what IntelliJ IDEA's navigation has that the IDE hasn't.  This plans four of its groups (In a
file, Between files, Symbols, and the search dialogs and their results; not Tool windows), written so another session
can take it over.  The user asked for it with "a focus on keeping code reusable" and added "a lot of the refactoring
code might be similar and reusable", so it is arranged by what is shared: first what is there to build on, then the
few shared pieces to build, then the features, each of which should come out as a thin user of those.

Nothing here is built, and writing it was not a go-ahead.  Each stage is the user's to start: bring it up with them,
say how you mean to do it, and go on when they say (NextIDEWork.txt's rule, and the user's: build the whole feature
as IntelliJ has it, not a cut-down one, and don't order the work by what is cheapest).  The stages are in an order
that builds each shared piece once, before its second user.  The user chose the order on 2026-11-20: A, B, D, C,
E, F, G, H (decision 1).

NextIDEWork.txt already has four of these as items the user has answered questions on: 2 (Find and Replace in the
file, with CRegex in BaseLib), 3 (Find in Files: regular expressions, file masks, Replace in Files), 4 (Go to Line)
and 7 (Bookmarks, with the user's keys).  They are placed in the stages here and what they share is said, but where
the two files differ NextIDEWork.txt's answers are the user's and win.

The facts about the code below were read from it on 2026-11-20 (commits HCP65-IDE 2cf7031, CommonLibraries
2267e5ece and the CTextArea enter event after it).  Lines move: find things by name.

What there is to build on
-------------------------

All in HCP65-IDE/HCP65IDE/HCP65IDE unless a library is named.  WindowLib, BaseLib and CppCompilerLib are in
CommonLibraries/Libraries.

The symbol at the caret
  - CIDEDocuments::FindSymbolPlace(line, column, role): "Every command that works on the symbol at the caret finds
    it here, so they all agree on where that is."  Then CIDECodeModel::GetSymbolAt (its key and kind), FindRoleAt,
    FindDefinition (the definition, else the declaration), GetSymbolLocations (every place of a key, each an
    SIDELocation: file, line, column, length, role, flags, usage, container), FindFileReferences (the caret
    usages' highlight) and FindRenameTarget.  CIDEDocuments::UpdateEditedTabsNow brings the index up to date first
    (CIDEEditorTab::IsIndexCurrent says whether it is).
  - CIDEContextActions::FindContext (Alt+Enter) already works out everything about the caret that a navigation
    command needs to know to be offered: SIDECaretContext has the symbol's key, kind and class, how many base and
    derived classes it has, whether it is declared, defined and virtual (FindSymbol, from the index), and whether
    the caret is in a function, a member function, an expression, a type or a macro (FindSyntax, from an unchecked
    parse).

What the index knows (CppCompilerLib's CCPPIndex, through CIDECodeModel)
  - Base and derived classes: CCPPIndexSymbol::maiBases and maiDerived; CIDECodeModel::FindClassBases(key, bAll,
    keys) and FindClassDerived(key, bAll, keys).
  - Overrides: CCPPIndex::FindOverrides; CIDECodeModel::FindOverriders(key, locations) (the derived classes' only)
    and FindOverrideLocations(key, locations) (both ways).  mbVirtual on the symbol.
  - Where each use is: SCPPIndexLocation::iContainer is the function or class definition the name is in (-1 at
    namespace scope; a lambda isn't one), and uiUsage says how it is used (CPPUT_Call, Read, Write, BaseClass...).
    CIDECodeModel::GetSymbolKey(iContainer, key, kind) names it.  Find Usages' grouping uses this (GetUsageGroup);
    nothing lists callers from it yet.
  - Declaration against definition: uiRole (CPPIR_Declaration, CPPIR_Definition, CPPIR_Reference).
  - What it doesn't know: where a declaration ends (only the name's place and length are kept); what a variable's,
    field's, parameter's or result's type is as a symbol (the type's name is only a reference at that place); a
    file's symbols in order (FindGoToSymbols and FindSymbolsDeclaredIn scan every symbol); the comment over a
    declaration; a symbol by its short name without a scan.

The syntax of a file
  - CIDERefactorUnit (IDERefactorUnit.h): a file parsed as its project builds it, from the text its editor has.
    FindTokenAt, FindNodeAt(line, column), FindAncestor(node, kind), GetRange(node, range), GetTree, and with
    bCheck a kept check for types (GetPass()->GetType(expression), AppendDeclaredType).  It parses each time; the
    refactorings each keep their own units for one operation (GetUnit and KillUnits, written seven times: Change
    Signature, Definitions, Safe Delete, Move Members, Move Class, Move Namespace, Convert Pointer).
  - "The function the caret is in" is FindAncestor(FindNodeAt(line, column), CPPS_FunctionDefinition), written out
    in five refactorings; its key is GetSymbolAt on the declarator's last name token.
  - CIDEChangeSignature::ReadSite fills an SIDESignatureSite for a function's declaration or definition: the
    ranges of its return type, its name, each parameter (all of it, its name, its default) and its body.
    CIDEDefinitions::FindFunction gives a function's declaration and definition as written (SIDEFunction).
    CIDEMoveMembers::ReadClass and ReadMembers (protected) give a class's range and each member's ranges and
    access.  CIDECodeModel::FindSiblingFunctions lists the functions declared beside one, in order.
  - The comment over a declaration: FindIDECommentStart(text, at) (IDEMoveMembers.h) is the start of the // lines
    directly above; CIDEDefinitions::FindBannerStart is the same for a definition's banner.  Neither handles /* */.
  - The edits thread (IDECodeModelEdits.cpp, ProcessEditedFile) parses an edited file once and makes its
    highlights, its index places and its syntax ranges, then throws the tree away.  A tab keeps the ranges
    (CIDEEditorTab::masSyntaxRanges, from CCPPHighlighter::FindSyntaxRanges) for Extend Selection; they have no
    kinds, so a tab can't tell a function's range from an expression's.  When they are behind the text,
    Extend Selection asks for the parse there and then (mcSyntaxBehind, to UpdateEditedTabsNow).
  - Brackets from the text alone: BaseLib's CTextNavigation::FindBracketsAround and FindClosingBracket (forwards
    only), and FindWordAround.

Going to a place
  - CIDEDocuments::OpenLocation(location, bSelectName) and OpenFile; both tell CIDENavigationHistory (BeginJump,
    EndJump), so anything that goes through them is on Back.  SetCaretPlace is a move the history doesn't record.
  - Places that follow edits: each open file has a CIDEDocumentAnchor; CIDEDocuments::DocumentChanged makes an
    SIDEPlaceChange and calls AdjustPlaces on the history, Find Usages, Find in Files and Duplicates, by name; each
    moves its places with AdjustIDEPlace(line, column, change).
  - CIDENavigationHistory keeps Back and Forward as SIDENavigationPlace (file, project, line, column), a hundred
    of them, for the session.

Lists of places
  - CIDEResultsPane: a tree, a CCodePreview across a CSplitContainer, and a toolbar down its left.  Filled with
    BeginShow, AddGroup, AddResult and EndShow; it asks its CIDEResultsSource where a result is and how to run
    again.  Find Usages, Find and Duplicates each use one.  CIDEFileLines reads the lines' text for the rows.
  - The tab for each search, and the pin, are in CIDEUsages (AddSearch, RemoveSearch, TabSelected, SetPinned), not

  - Next and Previous Occurrence: CIDEOccurrences steps whichever CIDESteppable has the keys or can be seen; the

      - FindImplementations(key, locations): a function's overriders, each one's definition if it has one; a
        class's derived classes; a declaration's definition.
      - FindTypeOf(file, line, column, key): the class, enum or typedef that is the type of the variable, field,
        parameter or function at a place.  The index doesn't link a symbol to its type.  Add the link in
        CCPPIndex::Gather (a symbol's type's symbol, where the type names one, through pointers, references and
        const): completion (NextIDEWork.txt's item 5) needs the members of a variable's type and would use the
        same link.  For an expression with no symbol of its own, the checked parse's type, as Introduce Variable's
        FindType (GetPass()->GetType, AppendType), its text looked up as a key the way
        CIDEMoveMembers::IsUsedThrough does.
      - FindCallers(key, callers): GetSymbolLocations' places with CPPUT_Call, by iContainer, each caller's key
        from GetSymbolKey, with its calls' places under it.
      - FindCallees(key, callees): the CPPUT_Call places whose container is the function.  The index has no list
        of a file's places (only place to symbol, mcLocations): either scan the symbols once and keep the answer
        for the hierarchy's life, or give CCPPIndex a list of each file's places, which RemoveFile would use too.
        Measure the scan on the ModPlay workspace before choosing.
    Enabling the commands: CIDEContextActions::FindContext's symbol half (FindSymbol) is made a function others
    can call, so Go to Implementation is offered exactly when Alt+Enter would say the symbol is virtual or a
    class with derived classes.

S6. What a symbol is, in words (IDE, CIDESymbolInfo).

    /* */ blocks and to skip a banner of slashes), where it is (its scope, its file and line), its kind's icon;
    for a function also each parameter's text and name, and its body's range.  It needs the declaring file
    parsed: a small cache of CIDERefactorUnits by file and change count (CIDEUnitCache), unchecked, which is also
    what the seven GetUnit and KillUnits copies in the refactorings are; each moves to it when its refactoring is
    next changed (decision 17).
    Users: Quick Definition, the declaration shown with Control held, Parameter Info, the chooser's and the Go to
    dialog's previews, the Structure rows' details, and completion's list when that is built; Quick
    Documentation and a name's tool tip if they are built (decision 11), which are what need the comment.

    Its places follow edits as the others' do.  Three things CIDEDocuments, CIDEOccurrences and CIDESettings do
